Cloud Security / Implementation Guide

AWS Security Hub 기반 클라우드 보안 태세 관리 구축

멀티 계정 AWS 환경에서 Security Hub를 활성화하고, 보안 표준 점검과 findings 집계, Lambda 자동 대응까지 이어지는 구축 절차를 정리합니다. 계정 단위 보안 점검을 조직 단위 보안 운영으로 확장하려는 엔지니어를 대상으로 합니다.

작성 기준일은 2026-03-19입니다.

적용 대상은 멀티 계정 AWS 환경의 보안 태세 관리(CSPM) 구성입니다.

핵심 명령은 aws securityhub enable-security-hub입니다.

주 출처는 원문 블로그 "AWS Security Hub Implementation"(2026-03-19)과 AWS Security Hub 공식 문서입니다.

요약

  • Security Hub는 여러 AWS 계정의 보안 상태를 하나의 화면으로 모아 보는 보안 태세 관리 서비스입니다. 명령 한 번으로 활성화되고, 기본 보안 표준 점검이 함께 시작됩니다.
  • GuardDuty, Inspector, Config 등 여러 서비스의 탐지 결과가 표준 형식(ASFF)의 findings로 정규화되므로, 서비스마다 다른 콘솔을 오가지 않고 한곳에서 우선순위를 판단할 수 있습니다.
  • 관리자 계정이 멤버 계정을 등록하면 조직 전체의 findings가 관리자 계정으로 집계됩니다. 계정이 늘어날수록 수동 점검이 불가능해지므로 멀티 계정 환경에서는 사실상 필수 구성입니다.
  • findings를 EventBridge로 받아 Lambda가 자동 조치하는 파이프라인까지 구성하면 탐지에서 대응까지 자동화됩니다. 단, 자동 조치는 비프로덕션 환경에서 먼저 검증한 뒤 적용하세요.

01Security Hub의 역할

AWS Security Hub는 여러 AWS 계정에 걸친 보안 태세를 종합적으로 보여주는 서비스입니다. 개별 보안 서비스가 각자의 콘솔에 탐지 결과를 쌓아두는 것과 달리, Security Hub는 GuardDuty(위협 탐지), Inspector(취약점 스캔), Config(구성 감사) 같은 서비스의 결과를 한곳으로 모읍니다.

이 집계가 가능한 이유는 모든 탐지 결과가 AWS Security Finding Format(ASFF)이라는 표준 JSON 스키마로 정규화되기 때문입니다. 어느 서비스가 만든 finding이든 심각도, 대상 리소스, 제목 같은 필드 구조가 동일하므로, 하나의 필터와 하나의 자동화 규칙으로 전체를 다룰 수 있습니다. 뒤에서 다룰 Lambda 자동 대응도 이 표준 형식 위에서 동작합니다.

Security Hub가 하는 일은 크게 세 가지입니다.

  • 보안 표준 기반 점검 - CIS, PCI DSS 같은 표준의 통제 항목으로 계정 구성을 자동 평가합니다.
  • findings 집계 - 여러 서비스, 여러 계정의 탐지 결과를 표준 형식으로 모읍니다.
  • 자동 대응 연계 - findings를 EventBridge로 흘려보내 자동 조치 파이프라인을 연결합니다.

원칙: Security Hub는 탐지 서비스가 아니라 탐지 결과를 모으고 평가하고 흘려보내는 허브입니다.

02Security Hub 활성화

활성화는 리전 단위이며 명령 한 번으로 끝납니다. 원문 예시는 서울 리전(ap-northeast-2)을 대상으로 하고, --enable-default-standards 플래그로 기본 보안 표준 점검을 함께 켭니다.

AWS CLI - EnableSecurityHub
aws securityhub enable-security-hub \
  --enable-default-standards \
  --region ap-northeast-2
참고 - 기본 표준의 범위

--enable-default-standards는 활성화 시점에 AWS가 기본으로 지정한 표준 (AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark)을 함께 켭니다. PCI DSS나 NIST SP 800-53 같은 표준은 기본에 포함되지 않으므로 필요하면 별도로 활성화해야 합니다.

활성화 직후부터 표준의 통제 항목별로 계정 구성이 자동 평가되고, 통과하지 못한 항목이 findings로 생성됩니다. Security Hub는 리전 서비스이므로 워크로드가 여러 리전에 걸쳐 있다면 리전별로 활성화 여부를 확인하세요.

03보안 표준 선택

Security Hub의 표준 기반 점검은 어떤 표준을 켜느냐에 따라 평가 항목이 달라집니다. 원문이 정리한 네 가지 표준은 다음과 같습니다.

표 1. Security Hub가 지원하는 주요 보안 표준
표준설명
AWS Foundational Security Best Practices AWS가 권고하는 보안 통제 모음입니다. 특별한 규제 요건이 없어도 기본으로 켜두는 표준입니다.
CIS AWS Foundations Benchmark Center for Internet Security가 정의한 AWS 구성 벤치마크입니다.
PCI DSS 카드 결제 산업의 데이터 보안 표준입니다. 결제 데이터를 다루는 워크로드에 적용합니다.
NIST SP 800-53 미국 연방 정보 시스템의 보안 통제 프레임워크입니다. 공공 규제 요건이 있을 때 적용합니다.

표준은 많이 켤수록 좋은 것이 아닙니다. 같은 리소스가 여러 표준에서 중복으로 걸리면 findings 수만 늘어나고 우선순위 판단이 흐려집니다. AWS Foundational Security Best Practices를 기준선으로 두고, 조직에 실제 규제 요건이 있는 표준만 추가하는 쪽이 운영하기에 낫습니다.

04멀티 계정 findings 집계

계정이 하나라면 지금까지의 구성으로 충분하지만, 실무 환경은 대부분 멀티 계정입니다. Security Hub는 관리자(administrator) 계정이 멤버(member) 계정을 등록하는 방식으로 findings를 한 계정에 집계합니다. 원문 예시는 멤버 생성과 초대 두 단계로 구성됩니다.

AWS CLI - 관리자 계정에서 실행
aws securityhub create-members \
  --account-details '[{"AccountId": "123456789012"}]'

aws securityhub invite-members \
  --account-ids "123456789012"

멤버 계정이 초대를 수락하면 해당 계정의 findings가 관리자 계정으로 흘러 들어오고, 보안팀은 관리자 계정 하나에서 조직 전체의 보안 태세를 봅니다. 계정별로 콘솔에 로그인해서 점검하는 방식은 계정이 늘어나는 속도를 따라가지 못하므로, 이 집계 구성이 멀티 계정 환경에서 Security Hub를 쓰는 실질적인 이유입니다.

참고 - 초대 방식과 Organizations 통합

위 명령은 계정을 하나씩 초대하는 수동 방식입니다. AWS Organizations를 쓰는 환경이라면 Security Hub의 Organizations 통합으로 조직 내 계정을 초대 절차 없이 자동 등록할 수 있습니다. 계정 수가 많거나 계정 생성이 잦다면 Organizations 통합이 관리 부담을 줄입니다.

05자동 대응 파이프라인

집계까지 구성하면 "보는 것"은 해결되지만, 대응은 여전히 사람 손에 남습니다. Security Hub는 모든 findings를 EventBridge 이벤트로 내보내므로, 규칙(rule)으로 특정 조건의 finding을 골라 Lambda에 전달하면 탐지에서 조치까지 자동화할 수 있습니다.

원문의 예시는 서버 측 암호화가 없는 S3 버킷 finding을 받아 KMS 기본 암호화를 설정하는 Lambda 함수입니다. 이벤트의 detail.findings 배열에서 finding을 꺼내 제목으로 유형을 판별하고, 대상 버킷에 조치를 적용합니다.

Lambda - Security Hub findings 자동 조치 핸들러 (Python)
import boto3

def lambda_handler(event, context):
    """Auto-remediate Security Hub findings."""

    finding = event['detail']['findings'][0]
    resource_type = finding['Resources'][0]['Type']

    if finding['Title'] == 'S3 bucket should have server-side encryption':
        s3 = boto3.client('s3')
        bucket_name = finding['Resources'][0]['Id'].split(':')[-1]

        s3.put_bucket_encryption(
            Bucket=bucket_name,
            ServerSideEncryptionConfiguration={
                'Rules': [{
                    'ApplyServerSideEncryptionByDefault': {
                        'SSEAlgorithm': 'aws:kms'
                    }
                }]
            }
        )

    return {'statusCode': 200}
주의 - 원문이 명시적으로 경고하는 부분

자동 조치는 반드시 비프로덕션 환경에서 먼저 테스트하세요. 위 예시처럼 리소스 설정을 직접 바꾸는 조치는 finding 판별 조건이 어긋나면 의도하지 않은 리소스를 수정합니다. 조치 대상을 제목 문자열이 아니라 통제 ID 같은 안정적인 식별자로 좁히고, EventBridge 규칙 단계에서도 심각도와 리소스 유형으로 한 번 더 거르는 것이 안전합니다.

06결론 및 권고

Security Hub는 규모가 커진 클라우드 환경에서 보안 태세를 유지하는 데 필수적인 서비스입니다. 자동 대응까지 결합하면 findings가 쌓이는 것을 지켜보는 수동 운영에서 벗어나 선제적인 보안 관리가 가능해집니다. 구축 순서는 다음과 같이 권고합니다.

  1. 각 리전에서 Security Hub를 활성화하고 기본 표준(AWS Foundational Security Best Practices, CIS) 점검을 켭니다.
  2. 규제 요건이 있는 경우에만 PCI DSS, NIST SP 800-53 같은 표준을 추가합니다.
  3. 관리자-멤버 구성(또는 Organizations 통합)으로 전 계정의 findings를 한 계정에 집계합니다.
  4. 반복적으로 발생하고 조치가 기계적인 finding부터 EventBridge와 Lambda로 자동 대응을 붙이되, 비프로덕션에서 검증한 뒤 확대합니다.

원칙: 집계를 먼저 완성하고 자동 대응은 검증된 finding 유형부터 좁게 시작합니다.
