Observability / Architecture Guide

OpenTelemetry 기반 EKS 엔드투엔드 관측성 구축 가이드

Amazon EKS 위에서 ADOT Collector를 배포하고 트레이스와 메트릭을 AWS X-Ray, CloudWatch로 내보내는 파이프라인 구성을 다룹니다. EKS 워크로드의 관측성 스택을 설계하는 운영자를 위한 문서입니다.

작성 기준일은 2026-03-19입니다.

적용 대상은 Amazon EKS에서 ADOT(AWS Distro for OpenTelemetry)로 관측성을 구축하는 컨테이너 워크로드입니다.

핵심 구성 요소는 adot EKS 애드온과 OpenTelemetryCollector 커스텀 리소스입니다.

주 출처는 whchoi98 기술 블로그 "Observability with OpenTelemetry on EKS"(2026-03-19)입니다.

요약

  • OpenTelemetry는 벤더 중립 관측성 프레임워크이고, AWS 배포판인 ADOT를 EKS 애드온 한 번의 설치로 클러스터에 올릴 수 있습니다.
  • 애플리케이션 파드는 OTLP(gRPC 4317, HTTP 4318)로 DaemonSet Collector에 텔레메트리를 보내고, Collector가 트레이스는 AWS X-Ray로, 메트릭은 CloudWatch EMF로 내보냅니다.
  • 파이프라인은 OpenTelemetryCollector 커스텀 리소스 하나에 receivers → processors → exporters 순서로 선언하며, batch processor가 전송을 묶어 오버헤드를 줄입니다.
  • 운영의 출발점은 p99 지연, 에러율, 파드 재시작 횟수, CPU/메모리 사용률 4개 지표에 임계값 경보를 Amazon Managed Grafana에 설정하는 것입니다.

01개요와 배경

관측성은 컨테이너 워크로드를 안정적으로 운영하기 위한 핵심 전제입니다. 파드가 수시로 생성되고 사라지는 EKS 환경에서는 개별 인스턴스에 로그인해서 문제를 추적하는 방식이 통하지 않으므로, 트레이스 / 메트릭 / 로그를 워크로드 바깥의 수집 계층으로 모아 두어야 장애 시점의 상태를 재구성할 수 있습니다.

OpenTelemetry는 이 수집 계층을 표준화한 벤더 중립 관측성 프레임워크입니다. 애플리케이션에는 언어별 SDK로 계측을 넣고, 텔레메트리는 OTLP라는 공통 프로토콜로 Collector에 보내며, 백엔드 선택은 Collector의 exporter 설정으로 분리합니다. 백엔드를 바꾸더라도 애플리케이션 코드를 다시 계측할 필요가 없다는 것이 이 구조의 핵심입니다.

AWS는 OpenTelemetry의 배포판으로 ADOT(AWS Distro for OpenTelemetry)를 제공합니다. ADOT에는 AWS X-Ray, CloudWatch 등 AWS 서비스로 내보내는 exporter가 포함되어 있고, EKS에서는 adot 애드온으로 설치할 수 있어 Collector 운영 부담이 줄어듭니다.

참고 - OpenTelemetry와 ADOT의 관계

ADOT는 별도의 제품이 아니라 AWS가 지원 범위를 검증해 배포하는 OpenTelemetry 배포판입니다. 계측 SDK와 Collector 구성 문법은 업스트림 OpenTelemetry와 동일하고, AWS 서비스용 exporter와 EKS 애드온 통합이 더해진 형태입니다.

02전체 아키텍처

구성의 뼈대는 단순합니다. SDK로 계측된 애플리케이션 파드가 같은 노드의 OTel Collector(DaemonSet)로 텔레메트리를 보내고, Collector가 신호 종류별로 AWS 백엔드에 나눠서 내보냅니다. 로그는 CloudWatch Logs로, 트레이스는 AWS X-Ray로, 메트릭은 CloudWatch 또는 AMP(Amazon Managed Service for Prometheus)로 향하며, 수집된 데이터는 AMG(Amazon Managed Grafana) 대시보드에서 함께 조회합니다.

이 구조에서 애플리케이션이 알아야 하는 것은 Collector의 OTLP 엔드포인트 하나뿐입니다. 백엔드 자격 증명, 재시도, 배치 전송 같은 운영 관심사는 모두 Collector 계층으로 내려가므로, 계측 코드와 전송 인프라의 수명 주기가 분리됩니다.

03ADOT Collector 배포

ADOT는 EKS 애드온으로 설치합니다. 애드온을 만들기 전에 Collector가 사용할 권한 리소스를 먼저 클러스터에 적용하고, 그다음 aws eks create-addon으로 애드온을 생성합니다.

터미널에서 실행 - ADOT 애드온 설치
kubectl apply -f https://amazon-eks.s3.amazonaws.com/docs/addons-otel-permissions.yaml    # 권한 리소스 선적용

aws eks create-addon \
  --cluster-name my-eks-cluster \
  --addon-name adot \
  --region ap-northeast-2
주의 - 권한 리소스를 먼저 적용해야 합니다

addons-otel-permissions.yaml 적용을 건너뛰고 애드온부터 생성하면 Collector 관련 리소스 생성이 권한 부족으로 실패합니다. 위 두 명령의 순서를 바꾸지 마세요.

3.1 Collector 배포 모드 선택

ADOT 애드온은 OpenTelemetry Operator 방식을 따르므로, Collector를 어떤 형태로 띄울지는 OpenTelemetryCollector 리소스의 mode 필드로 정합니다. 이 문서의 구성은 노드마다 Collector를 하나씩 두는 daemonset 모드를 사용합니다. 파드가 같은 노드의 Collector로 보내므로 전송 홉이 짧고, 노드 수에 비례해 수집 용량이 늘어납니다.

표 1. OpenTelemetry Collector 배포 모드 (OpenTelemetry Operator 기준)
모드배치 형태적합한 상황
deployment 중앙 게이트웨이형 Collector 파드 여러 소스의 텔레메트리를 한곳에 모아 공통 처리(샘플링, 필터링)를 할 때
daemonset 노드당 1개 (본 문서 구성) 노드 로컬 수집, 애플리케이션과 가까운 지점에서의 배치 전송
statefulset 안정적 식별자를 가진 파드 집합 타깃 할당 등 Collector 인스턴스별 상태가 필요할 때
sidecar 애플리케이션 파드에 컨테이너로 동승 파드 단위 격리가 필요하거나 워크로드별 구성이 크게 다를 때

04Collector 파이프라인 구성

Collector 구성은 receivers → processors → exporters의 3단 파이프라인으로 선언합니다. 아래 구성은 OTLP receiver로 트레이스와 메트릭을 받고, batch processor로 묶은 뒤, 트레이스는 awsxray exporter로, 메트릭은 awsemf exporter로 내보냅니다.

OpenTelemetryCollector 커스텀 리소스 - adot-collector.yaml
apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: adot-collector
spec:
  mode: daemonset
  config: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318

    processors:
      batch:
        timeout: 10s

    exporters:
      awsxray:
        region: ap-northeast-2
      awsemf:
        region: ap-northeast-2
        namespace: EKS/Application

    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [batch]
          exporters: [awsxray]
        metrics:
          receivers: [otlp]
          processors: [batch]
          exporters: [awsemf]

각 단계의 역할은 다음과 같습니다. 파이프라인은 신호 종류(traces, metrics)별로 독립적으로 정의되므로, 같은 receiver를 공유하면서 신호마다 다른 백엔드로 보낼 수 있습니다.

표 2. 파이프라인 구성 요소별 역할
구성 요소이 구성에서의 값역할
receivers otlp (gRPC 4317, HTTP 4318) SDK가 보내는 OTLP 텔레메트리를 표준 포트에서 수신합니다.
processors batch (timeout 10초) 개별 스팬 / 데이터포인트를 묶어 내보내 전송 횟수와 오버헤드를 줄입니다.
exporters awsxray, awsemf 트레이스는 X-Ray 세그먼트로, 메트릭은 CloudWatch EMF 로그 기반 메트릭으로 변환해 내보냅니다.
참고 - awsemf의 namespace

awsemf exporter의 namespace: EKS/Application은 CloudWatch 메트릭 네임스페이스를 지정합니다. CloudWatch 콘솔에서 이 이름으로 커스텀 메트릭을 찾게 되므로, 팀의 네임스페이스 규칙에 맞춰 정한 뒤 바꾸지 않는 것이 좋습니다.

05핵심 모니터링 지표

파이프라인이 흐르기 시작하면 다음 4개 지표부터 경보를 설정합니다. 원문이 제시하는 임계값은 일반적인 웹 워크로드 기준의 출발점이며, 서비스 특성에 맞게 조정합니다.

표 3. 핵심 지표와 경보 임계값 (원문 기준)
지표설명경보 임계값
요청 지연 (p99) 99번째 백분위수 응답 시간 500ms 초과
에러율 5xx 응답 / 전체 요청 1% 초과
파드 재시작 횟수 컨테이너 크래시 빈도 5분 내 3회 초과
CPU / 메모리 사용률 리소스 소비량 80% 초과
주의 - 프로덕션에서는 경보 규칙까지가 구축입니다

원문은 프로덕션 워크로드라면 Amazon Managed Grafana에 경보 규칙을 설정하라고 강조합니다. 대시보드만 만들고 경보를 미루면 지표가 쌓여도 장애를 사람이 발견하는 구조가 그대로 남습니다.

06결론

OpenTelemetry는 계측과 백엔드를 분리하는 벤더 중립 관측성 프레임워크이고, ADOT는 이를 AWS 환경에 맞게 배포판으로 제공합니다. EKS에서는 애드온 설치와 OpenTelemetryCollector 리소스 하나로 트레이스 / 메트릭 / 로그가 X-Ray, CloudWatch, AMP 같은 AWS 네이티브 서비스로 흘러가는 파이프라인을 구성할 수 있습니다.

적용 순서는 권한 리소스 적용 → adot 애드온 생성 → Collector 파이프라인 선언 → 4개 핵심 지표 경보 설정입니다. 계측 코드는 OTLP 표준만 바라보므로, 이후 백엔드를 바꾸거나 추가하더라도 Collector 설정 변경으로 흡수됩니다.

원칙: 애플리케이션은 Collector만 바라보게 하고, 백엔드 선택과 경보 운영은 Collector 설정과 Grafana 규칙으로 분리합니다.
