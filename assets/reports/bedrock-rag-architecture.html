Amazon Bedrock 기반 RAG 아키텍처 구성

Amazon Bedrock Knowledge Base, OpenSearch Serverless, S3를 조합해 관리형 RAG 파이프라인을 구성하는 방법을 정리합니다. 청크 전략과 임베딩 모델 선택, 벡터 스토어 비용 고려사항까지 다룹니다.

작성 기준일은 2026-03-19입니다.

적용 대상은 Amazon Bedrock Knowledge Base로 RAG 시스템을 구축하려는 워크로드입니다.

핵심 API는 bedrock-agent-runtime의 retrieve_and_generate입니다.

주 출처는 원문 블로그 "Building RAG with Amazon Bedrock"(2026-03-19)과 Amazon Bedrock 공식 문서입니다.

요약

  • Amazon Bedrock Knowledge Base는 문서 수집, 청킹, 임베딩, 검색을 관리형으로 자동 처리하므로 RAG 파이프라인을 직접 구현할 필요가 없습니다.
  • 애플리케이션은 retrieve_and_generate API 호출 하나로 검색과 답변 생성을 함께 수행하고, 벡터 저장은 OpenSearch Serverless, 원본 문서 보관은 S3가 담당합니다.
  • OpenSearch Serverless는 최소 2 OCU가 항상 과금되어 원문 기준 월 최소 $345.60의 고정 비용이 발생하므로, 소규모 워크로드는 이 비용을 먼저 검토해야 합니다.
  • 검색 정확도를 높이려면 semantic chunking을 적용하고, 다국어 지원이 필요하면 임베딩 모델로 Amazon Titan Text Embeddings v2를 선택하며, CloudWatch로 검색 지연을 모니터링합니다.

01RAG와 Bedrock Knowledge Base

Retrieval-Augmented Generation(RAG)은 대규모 언어 모델의 일반 지식에 조직 내부의 지식 베이스를 결합하는 기법입니다. 사용자 질의가 들어오면 먼저 내부 문서에서 관련 내용을 검색하고, 검색된 내용을 근거로 모델이 답변을 생성합니다. 모델을 재학습하지 않고도 조직 고유의 최신 정보를 답변에 반영할 수 있습니다.

이 파이프라인을 직접 구축하려면 문서 수집, 청킹, 임베딩 생성, 벡터 인덱싱, 검색까지 여러 단계를 각각 구현하고 운영해야 합니다. Amazon Bedrock Knowledge Base는 이 전체 과정을 관리형으로 자동 처리하므로, 애플리케이션은 API 호출 한 번으로 검색과 답변 생성을 수행할 수 있습니다.

참고 - RAG와 파인튜닝의 차이

RAG는 모델 가중치를 바꾸지 않고 프롬프트에 검색 결과를 주입하는 방식입니다. 문서가 갱신되면 데이터 소스를 다시 동기화하는 것만으로 답변에 반영되므로, 자주 바뀌는 사내 문서에는 파인튜닝보다 RAG가 적합합니다.

02전체 아키텍처

아키텍처는 애플리케이션(Lambda), Bedrock Knowledge Base, OpenSearch Serverless 벡터 스토어, S3 문서 스토어의 네 계층으로 구성됩니다. 사용자 질의는 애플리케이션을 거쳐 Knowledge Base로 전달되고, Knowledge Base가 벡터 스토어에서 관련 청크를 검색해 답변을 생성합니다.

데이터 흐름은 두 갈래입니다. 수집 경로에서는 S3에 올린 원본 문서를 Knowledge Base가 청크로 나누고 임베딩으로 변환해 OpenSearch Serverless 인덱스에 기록합니다. 질의 경로에서는 사용자 질의를 같은 임베딩 모델로 벡터화해 유사한 청크를 검색하고, 검색 결과를 근거로 파운데이션 모델이 답변을 생성합니다.

03핵심 구성 요소

3.1 Amazon Bedrock Knowledge Base

Knowledge Base는 문서 수집, 청킹, 임베딩, 검색을 자동으로 처리하는 파이프라인의 중심입니다. 애플리케이션에서는 bedrock-agent-runtime 클라이언트의 retrieve_and_generate 하나로 검색과 답변 생성을 함께 요청합니다.

Python (boto3) - retrieve_and_generate 호출
import boto3

bedrock_agent = boto3.client('bedrock-agent-runtime', region_name='us-east-1')

response = bedrock_agent.retrieve_and_generate(
    input={'text': 'What is the backup policy?'},
    retrieveAndGenerateConfiguration={
        'type': 'KNOWLEDGE_BASE',
        'knowledgeBaseConfiguration': {
            'knowledgeBaseId': 'YOUR_KB_ID',
            'modelArn': 'arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-sonnet-4-20250514'
        }
    }
)

knowledgeBaseId로 어느 지식 베이스를 검색할지, modelArn으로 답변 생성에 쓸 파운데이션 모델을 지정합니다. 검색만 수행하고 생성은 직접 제어하고 싶다면 retrieve API로 청크만 받아 프롬프트를 구성하는 방식도 가능합니다.

3.2 벡터 스토어 - OpenSearch Serverless

OpenSearch Serverless는 문서 임베딩을 저장하는 관리형 벡터 데이터베이스입니다. 클러스터 용량 관리 없이 벡터 인덱스를 운영할 수 있어 Knowledge Base의 기본 벡터 스토어 선택지로 쓰입니다.

주의 - 원문이 명시한 최소 고정 비용

OpenSearch Serverless는 최소 2 OCU가 항상 필요하며, 원문 기준 월 최소 $345.60이 과금됩니다. 사용량이 적어도 발생하는 고정 비용이므로, 소규모 또는 개인 실습 워크로드라면 이 비용이 전체 아키텍처 비용의 대부분을 차지할 수 있습니다.

3.3 문서 스토어 - Amazon S3

S3는 Knowledge Base에 공급되는 원본 문서를 저장합니다. S3 버킷을 데이터 소스로 연결한 뒤 동기화(sync)를 실행하면 Knowledge Base가 문서를 읽어 청킹과 임베딩을 수행합니다. 문서가 추가되거나 갱신되면 동기화를 다시 실행해 인덱스를 최신 상태로 유지합니다.

04청크 전략과 임베딩 모델

검색 정확도는 문서를 어떤 단위로 나누는지에 크게 좌우됩니다. Knowledge Base는 수집 시점에 문서를 청크로 분할하고 청크 단위로 임베딩을 생성하므로, 청크 전략이 검색 품질의 출발점입니다. 원문의 권고는 semantic chunking을 사용해 검색 정확도를 높이는 것입니다.

표 1. Bedrock Knowledge Base가 지원하는 청크 전략 (Bedrock 공식 문서 기준)
전략동작적합한 경우
기본 / 고정 크기 기본 설정은 약 300토큰 단위로 분할하며, 고정 크기 설정에서는 청크당 토큰 수와 청크 간 중첩 비율을 지정합니다. 문서 구조가 단순하고 빠르게 시작할 때
Hierarchical 부모-자식 청크의 중첩 구조로 저장하고, 검색 시 자식 청크를 부모 청크로 교체해 더 넓은 문맥을 전달합니다. 정밀한 매칭과 넓은 문맥이 모두 필요할 때
Semantic 문장 간 의미 유사도를 기준으로 경계를 정해 의미 단위로 분할합니다. 검색 정확도가 우선일 때 (원문 권고)
참고 - semantic chunking의 추가 비용

Bedrock 공식 문서에 따르면 semantic chunking은 분할 경계를 판단하는 데 파운데이션 모델을 사용하므로, 데이터 양에 비례하는 추가 비용이 발생합니다. 정확도 이득과 수집 비용을 함께 비교해 선택합니다.

임베딩 모델로 원문은 다국어 지원을 위해 Amazon Titan Embeddings v2를 권고합니다. Bedrock 공식 문서 기준으로 Titan Text Embeddings V2(amazon.titan-embed-text-v2:0)는 최대 8,192토큰을 입력받아 기본 1,024차원 벡터를 출력하고, 512차원과 256차원도 선택할 수 있습니다. 질의와 문서는 반드시 같은 임베딩 모델로 벡터화되어야 유사도 비교가 의미를 가지므로, 임베딩 모델은 지식 베이스 생성 시점에 정해 유지합니다.

05모니터링과 모범 사례

RAG 시스템의 응답 시간은 검색 단계와 생성 단계의 합입니다. 원문은 CloudWatch 지표를 활성화해 검색 지연(retrieval latency)을 추적할 것을 권고합니다. 검색 단계가 느려지면 전체 응답이 함께 느려지므로, 검색 지연을 별도 지표로 관찰해야 병목 구간을 구분할 수 있습니다.

표 2. 원문이 제시한 모범 사례 요약
영역권고
청크 전략 semantic chunking을 사용해 검색 정확도를 높입니다.
임베딩 모델 다국어 지원이 필요하면 Amazon Titan Embeddings v2를 사용합니다.
모니터링 CloudWatch 지표를 활성화해 검색 지연을 추적합니다.

06결론

Amazon Bedrock Knowledge Base는 문서 수집부터 검색까지 RAG 파이프라인 전체를 관리해 구현 부담을 크게 줄입니다. OpenSearch Serverless와 S3를 조합하면 확장 가능한 프로덕션 수준의 RAG 시스템을 구성할 수 있습니다. 다만 OpenSearch Serverless의 최소 OCU 고정 비용은 워크로드 규모와 무관하게 발생하므로 설계 초기에 반영해야 합니다.

원칙: 파이프라인 구현은 Knowledge Base에 맡기고, 설계 판단은 청크 전략, 임베딩 모델, 벡터 스토어 비용 세 가지에 집중합니다.

원문은 실습을 위한 자료로 Bedrock RAG Workshop의 공개를 예고하고 있습니다.
