AIML / Architecture Deep Dive

ontology-for-mfg: 하이테크 제조 온톨로지 PoC 아키텍처 분석

22개 온톨로지 클래스로 제조 도메인(BOM, 공급망, 표준/규제, 품질, 운영)을 지식 그래프로 모델링하고, 그 위에 Bedrock 에이전트와 12개 시나리오를 올린 PoC의 구조를 코드와 스키마 기준으로 분석합니다.

작성 기준일은 2026-08-09입니다.

분석 대상은 ontology-for-mfg v0.5.6(2026-05-15 릴리스)입니다.

온톨로지 정의 파일은 ontology/schema.ttl, 에이전트 진입점은 api/services/agent.py입니다.

주 출처는 GitHub 저장소 whchoi98/ontology-for-mfg의 코드, 스키마, docs/ 문서입니다.

요약

  • ontology-for-mfg는 22개 클래스와 24개 관계로 하이테크 제조 도메인을 Neptune 지식 그래프로 모델링하고, 그 위에 12개 시나리오(A-L)와 5개 페르소나를 올린 PoC입니다. 수치는 전부 schema.ttl과 코드에서 직접 확인한 값입니다.
  • Bedrock converse_stream 기반 에이전트가 도구 5종(search_semantic, neptune_query, kb_retrieve, compliance_check, memory_save)을 최대 8라운드 호출하며, 답변은 SSE로 토큰 단위 스트리밍됩니다.
  • 제조 고유의 차별점은 BOM 4계층(Product, Module, Component, RawMaterial), 표준/규제 4클래스(JEDEC부터 CBAM까지 10개 체계), 그리고 같은 질문을 페르소나별 KPI 어조로 다르게 프레이밍하는 구조입니다.
  • 라이브 데모는 https://mfg-ontology.whchoi.net (Cognito 보호)에서 동작합니다. 다만 약 10,644개 노드의 합성 데이터 기반 PoC이므로 실제 협력사, 부품 정보는 포함하지 않습니다.

01제조 도메인에서 온톨로지가 푸는 문제

하이테크 제조의 데이터 질문은 대부분 관계를 여러 단계 따라가야 답이 나옵니다. "이 제품에 들어가는 부품 중 REACH 규제 물질을 포함한 것은 무엇인가"라는 질문 하나가 제품 → 모듈 → 부품 → 물질 → 규제로 이어지는 4단계 이상의 조인을 요구합니다. 관계형 테이블로도 답할 수는 있지만, 질문이 바뀔 때마다 조인 경로를 다시 설계해야 하고 LLM이 스스로 질의를 만들기도 어렵습니다.

이 프로젝트가 온톨로지로 명시한 제조 고유의 관계 사슬은 세 갈래입니다. 첫째, BOM 계층입니다. Product -hasModule-> Module -consistsOf-> Component -madeOf-> RawMaterial로 제품 구조가 4계층 그래프로 내려갑니다. 둘째, 규제 추적입니다. Component -containsSubstance-> Substance -regulatedBy-> Regulation 사슬이 있어서 부품에서 출발해 REACH-SVHC, RoHS 해당 여부를 그래프 탐색만으로 판정할 수 있습니다. 셋째, 품질 추적입니다. QualityIncident -about-> Component, EightDReport -addresses-> QualityIncident, EightDReport -identifies-> RootCause -linkedTo-> Supplier로 품질 사고에서 근본 원인, 책임 협력사까지 한 그래프 안에서 연결됩니다.

표준과 규제를 데이터가 아니라 클래스로 승격한 점이 자매 프로젝트인 리테일 편과 갈라지는 지점입니다. Standard, Certification, Regulation, Substance 4개 클래스가 스키마에 존재하고, JEDEC, IPC, AEC-Q, IATF 16949, ISO 9001, REACH-SVHC, RoHS, CBAM, IRA, USMCA 10개 체계의 실제 표준 데이터 서브셋이 data/public/에 적재됩니다. 부품의 인증 여부와 무역 규제 노출이 그래프 질의 대상이 되는 것입니다.

참고 - 이 문서에서 말하는 온톨로지

여기서 온톨로지는 OWL 추론기까지 쓰는 무거운 시맨틱 웹 스택이 아니라, schema.ttl에 OWL 문법으로 정의한 클래스/관계 정의를 Neptune 프로퍼티 그래프의 라벨과 엣지 타입으로 옮겨 쓰는 실용적 스키마를 뜻합니다. 질의는 SPARQL이 아니라 openCypher로 합니다.

2.2 AWS 아키텍처

실행 환경은 전부 AWS 관리형 서비스입니다. 지식 그래프는 Amazon Neptune(openCypher, VPC 내부 전용), 의미 검색은 Amazon OpenSearch Serverless(VECTORSEARCH 컬렉션, 한국어 Nori 분석기 + k-NN HNSW), LLM은 Amazon Bedrock Converse API, 컴퓨트는 ECS Fargate ARM64 서비스 2개(api, web), 엣지는 CloudFront와 ACM 커스텀 도메인, 인증은 Amazon Cognito입니다. 인프라 전체는 AWS CDK v2(TypeScript) 6개 스택(network, data, ai, compute, edge, observability)으로 정의됩니다.

03핵심 메커니즘 딥다이브

3.1 에이전트 tool-use 루프: 도구 5종

대화형 에이전트(시나리오 B)의 중심은 api/services/agent.py의 AgentRunner입니다. Bedrock converse_stream을 호출하고, 모델이 도구를 요청하면 실행 결과를 대화에 되돌려주는 루프를 최대 8라운드(max_rounds=8) 돕니다. v0.5.6부터는 contentBlockDelta 텍스트 청크가 도착하는 즉시 SSE delta 이벤트로 전달되어, 저장소 CHANGELOG 기준 첫 토큰까지의 시간이 2-5초에서 300-600ms 수준으로 줄었습니다.

표 3. 에이전트 도구 5종 (api/routers/chat.py의 _TOOLS)
도구역할백엔드

안정성 장치가 두 겹입니다. 첫째, 8D 파이프라인(및 ops 평가 실행) 등 동기식 Bedrock 호출은 ThreadPoolExecutor.submit().result(timeout=25)로 25초 타임아웃에 묶이고, 초과하면 결정적 템플릿으로 폴백합니다(ADR-003). 채팅은 converse_stream 스트리밍으로 별도 처리됩니다. 둘째, 데이터 경로가 죽어도 데모가 빈 화면이 되지 않도록 결정형 시나리오 대부분(10개 라우터)에 합성 폴백과 _synthetic 플래그가 있고, 검색(A)과 채팅(B)에는 없습니다.

주의 - LLM에게 그래프 질의를 맡길 때의 방어선

neptune_query는 모델이 직접 Cypher를 작성하는 도구라서 프롬프트 인젝션으로 쓰기 질의가 흘러들 수 있습니다. 이 프로젝트는 chat.py:_tool_neptune에서 CREATE, DELETE, SET, MERGE, DROP 등을 정규식 거부 목록으로 차단하는 읽기 전용 게이트웨이를 두고(ADR-002), 사용자 제공 라벨은 22클래스 허용 목록으로만 통과시킵니다. 같은 구조를 만들 때 이 계층을 생략하면 에이전트가 그래프를 변조할 수 있는 경로가 그대로 열립니다.

3.2 하이브리드 검색: BM25 + k-NN + RRF

의미 검색(시나리오 A)은 두 검색을 병렬로 돌려 합칩니다. 한국어 Nori 분석기 기반 BM25와 Titan 1,024차원 임베딩 k-NN을 각각 50건씩 뽑고, Reciprocal Rank Fusion(k=60)으로 순위를 융합해 상위 10건을 반환합니다. OpenSearch Serverless에는 search pipeline 모듈이 없어서 RRF 융합을 Python에서 직접 수행합니다.

api/services/search.py - RRF 융합 (발췌)
@staticmethod
def rrf(hit_lists: list[list[dict]], k: int = 60) -> list[tuple[str, float]]:
    scores: dict[str, float] = {}
    for hits in hit_lists:
        for rank, h in enumerate(hits, start=1):
            doc_id = h["_id"]
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)

설계 의도는 상호 보완입니다. BM25는 부품 번호나 표준 이름 같은 정확한 토큰에 강하고, k-NN은 "차량용 고온 환경 커패시터"처럼 표현이 다른 질의에 강합니다. Bedrock 리랭커 단계는 코드에 준비되어 있으나 ap-northeast-2 미제공으로 현재 배포에서는 비활성입니다.

3.3 페르소나별 프레이밍

같은 화면, 같은 질문이라도 보는 사람의 KPI가 다릅니다. 이 프로젝트는 Buyer, Engineer, Quality, SCM, Plant 5개 페르소나를 라우팅이 아닌 런타임 컨텍스트로 다룹니다. 웹에서는 단일 useActivePersona() 컨텍스트가 12개 시나리오 화면의 프레이밍을 바꾸고, API에서는 시스템 프롬프트가 persona 값으로 포맷됩니다. 페르소나별 라우트 디렉터리를 만들었다가 v0.5.2에서 제거한 이력이 CLAUDE.md에 남아 있습니다.

매 턴이 끝나면 api/services/followups.py가 Haiku(300 토큰 한도)로 한국어 후속 질문 3개를 생성해 SSE suggested_followups 이벤트로 내보냅니다. 이때 페르소나별 어조 맵이 들어갑니다. Buyer는 단가, 리드타임, MOQ 방향으로, Engineer는 스펙과 AEC-Q, JEDEC 인증 방향으로, Quality는 8D와 REACH-SVHC 방향으로, SCM은 TradeLane과 IRA, CBAM 방향으로, Plant는 OEE와 텔레메트리 방향으로 질문이 기울어집니다. 생성 실패 시에는 빈 배열로 조용히 폴백합니다.

3.4 대표 시나리오 패턴: 8D / RCA

8D 보고서 시나리오(J)는 이 아키텍처의 조합 방식을 가장 잘 보여줍니다. 그래프에는 QualityIncident에서 EightDReport, RootCause를 거쳐 Supplier까지 이어지는 품질 사슬이 있고, 보고서 초안은 api/services/eight_d_writer.py가 작성합니다. Haiku가 emit_eight_d 도구를 정확히 한 번 호출하도록 강제하고, 도구 스키마가 8개 필수 문자열 필드(D1-D8)를 요구하므로 출력 형식이 프롬프트가 아니라 스키마로 보장됩니다. maxTokens=1500으로 25초 예산 안에 들어옵니다.

원칙: 정형 출력은 작은 모델 + tool-use 스키마로, 자유 추론은 큰 모델 + 도구 루프로 푼다는 분리가 이 프로젝트 전체를 관통합니다(ADR-001).

0412개 시나리오 개관

시나리오 A부터 L까지가 제조 라이프사이클을 덮습니다. 각 시나리오는 api/routers/의 라우터 하나와 웹 페이지 하나로 대응되며, 아래 핵심 엔진 열은 각 라우터가 실제로 import하는 서비스 기준입니다. LLM이 개입하는 것은 B, J 계열이고 나머지 다수는 그래프 질의와 결정적 도메인 엔진의 조합입니다.

05실제 운영: 배포, 인증, 라이브 데모

5.1 배포 파이프라인

CI는 GitHub Actions 3개 병렬 잡(api: pytest, web: tsc + next build, cdk: Jest 불변식 테스트)이고, 이미지 배포는 수동입니다. ARM64 이미지를 빌드해 ECR에 푸시한 뒤 ECS 서비스를 강제 재배포합니다. v0.5.6 기준 pytest 스위트는 175개가 통과합니다.

배포 - 개발 호스트에서 실행 (CLAUDE.md의 절차)
docker build --platform linux/arm64 -f api/Dockerfile -t <ecr>/ontology-mfg-dev-api:latest .
docker push <ecr>/ontology-mfg-dev-api:latest
aws ecs update-service --cluster ontology-mfg-dev-cluster \
  --service ontology-mfg-dev-api --force-new-deployment   # 롤링 재배포 ~3-5분

5.2 인증과 가드레일

전체 사이트는 Amazon Cognito User Pool(us-east-1)로 보호되고, API 미들웨어가 JWT를 검증합니다. /healthz 같은 경로만 예외입니다. 여기에 Bedrock Guardrails가 제조 특화 4개 토픽(기밀 IP, 경쟁사 비방, 규제 위반, 유해 화학물질)을 걸러 개입 내역을 운영 콘솔에서 노출합니다. Neptune과 OpenSearch는 VPC 내부 전용이라 외부에서 직접 접근할 수 없고 API 태스크 롤로만 접근이 허용됩니다.

5.3 라이브 데모와 운영 콘솔

라이브 데모는 https://mfg-ontology.whchoi.net 에서 동작하며 Cognito 로그인이 필요합니다 (계정은 프로젝트 소유자를 통해 발급). 운영 콘솔에는 30개 제조 도메인 질의를 재실행해 점수를 매기는 평가 보드(/api/ops/eval)와 최근 200개 tool_call 이벤트를 보여주는 트레이스 링 버퍼(/api/ops/trace)가 있어, 에이전트가 어떤 도구를 어떤 인자로 불렀는지 배포 환경에서 바로 확인할 수 있습니다.

참고 - SSE와 CloudFront의 궁합

토큰 스트리밍은 중간의 어떤 계층이라도 버퍼링하면 무너집니다. 이 프로젝트는 CloudFront의 origin 압축을 SSE 경로에서 비활성화하고(ADR-007), Lambda@Edge를 viewer request(인증)에만 붙여 origin response 단계의 버퍼링을 피했습니다. SSE가 배포에서만 한 덩어리로 도착한다면 이 두 지점을 먼저 확인할 필요가 있습니다.

06한계

이 프로젝트는 PoC이고, 저장소 스스로도 그렇게 선언합니다. 문서를 근거로 도입 판단을 하기 전에 다음 경계를 확인해야 합니다.

  • 합성 데이터입니다. 그래프의 약 10,644개 노드는 생성기가 만든 것으로, 실제 협력사와 부품 정보는 포함하지 않습니다. 표준/규제 데이터만 실제 체계의 서브셋입니다. 실데이터 규모(수백만 노드)에서의 Neptune 질의 성능은 검증되지 않았습니다.
  • 리랭커가 비활성 상태입니다. ap-northeast-2 미제공으로 검색 품질은 RRF 융합까지만 반영되어 있고, 코드의 리랭크 단계는 현재 배포에서 통과(pass-through)합니다.
  • 이미지 배포가 수동입니다. CI는 테스트만 수행하고, ECR 푸시와 ECS 재배포는 사람이 실행합니다.
  • Cypher 읽기 전용 게이트웨이는 정규식 거부 목록 기반입니다. 방어층으로 유효하지만, 프로덕션이라면 권한 분리(읽기 전용 엔드포인트나 IAM 정책 수준의 제약)를 병행하는 편이 안전합니다.
  • 데모가 Cognito로 잠겨 있어 문서만으로는 화면을 검증할 수 없습니다. 코드와 docs/의 서술이 1차 근거입니다.
  • 수치 검증 과정에서 문서와 코드의 어긋남은 발견하지 못했습니다. 22클래스, 도구 5종, 페르소나 5종, 시나리오 12종 모두 README 서술과 schema.ttl, 코드가 일치합니다. 다만 docs/architecture.md의 "16 routers" 서술은 라우터 파일 15개에 main.py의 /healthz 엔드포인트를 더해 세어야 맞습니다.

07결론

ontology-for-mfg가 보여주는 것은 "LLM에 제조 데이터를 붙이는" 일반론이 아니라 역할 분리의 구체적인 배치입니다. 도메인 지식은 22클래스 스키마와 그래프에, 정확한 계산은 결정적 엔진에, 모호한 질의 해석과 서술만 LLM에 둡니다. 그 결과 12개 시나리오 중 LLM이 필요한 것은 2개(B, J)뿐이고, 나머지는 재현 가능한 그래프 질의로 답합니다.

제조 도메인에 온톨로지 기반 에이전트를 검토한다면 이 저장소에서 가져갈 수 있는 재사용 가능한 패턴은 네 가지입니다. BOM과 규제를 클래스로 승격한 스키마 설계, 읽기 전용 Cypher 게이트웨이, Sonnet/Haiku 역할 분리와 25초 타임아웃 + 결정적 폴백, 그리고 페르소나를 라우팅이 아닌 런타임 컨텍스트로 다루는 프레이밍 구조입니다. 코드는 GitHub에 공개되어 있으므로 schema.ttl과 api/services/agent.py부터 읽기 시작하는 것을 권합니다.
