ontology-for-retail - 한국 리테일/CPG 지식그래프 PoC 아키텍처 분석

도메인 온톨로지 하나가 13개 리테일 경험 시나리오를 어떻게 구동하는지, Neptune openCypher / OpenSearch Serverless / Bedrock / AgentCore 조합의 실제 코드와 데이터를 기준으로 분석합니다.

작성 기준일은 2026-08-09입니다.

분석 대상은 로컬 저장소 ontology-for-retail(FastAPI + Next.js 14 + AWS CDK v2 모노레포, 마지막 커밋 c852ba0, 2026-05-09)입니다.

핵심 백엔드는 Neptune openCypher, OpenSearch Serverless, Bedrock Sonnet 4.6, AgentCore Memory이며, Code Interpreter 래퍼는 존재하나 아직 미배선입니다.

본문의 모든 수치는 저장소의 코드(api/)와 데이터(data/output/)에서 직접 확인한 값입니다.

요약

  • ontology-for-retail은 한국 리테일/CPG 도메인 온톨로지(노드 클래스 25종 / 관계 40종)로 13개 시나리오(A-M)와 메타 페이지 /codegraph를 구동하는 30-60분 PoC 데모입니다.
  • 검색은 Nori BM25와 Cohere KNN을 RRF(k=60)로 융합한 뒤 rerank-v3로 재정렬하고, 에이전트는 Bedrock Converse 루프에 7개 도구와 AgentCore Memory(단기 세션 + 장기 사용자 네임스페이스)를 결합합니다.
  • README와 docs 일부는 코드보다 낡았습니다. README는 시나리오 B의 도구를 4개로, architecture.md는 노드 클래스를 19종으로 기술하지만 코드 기준은 각각 7개 도구, 25종 클래스입니다. 이 문서는 코드/데이터 기준으로 씁니다.
  • 결론 - 관리형 AI 서비스와 그래프 스키마를 엮는 패턴 카탈로그로는 유효하지만, 데이터가 전부 합성이고 보안이 데모 태세이므로 수치를 실측 성능이나 운영 기준으로 읽으면 안 됩니다.

01왜 리테일 경험에 도메인 온톨로지인가

리테일에서 실제로 가치 있는 질문은 대부분 관계 질문입니다. "임산부가 피해야 할 성분이 든 상품은 무엇인가", "이 상품의 같은 카테고리 다른 브랜드 대체재는 무엇인가", "캠핑족 회원은 어느 채널에서 어떤 가격을 만나는가" 같은 질문은 문서 검색만으로는 답이 나오지 않습니다. 상품, 성분, 페르소나, 채널, 회원, 물류 거점이 어떻게 연결되는지가 답의 재료이기 때문입니다.

ontology-for-retail은 이 관계들을 Neptune 지식그래프의 명시적 스키마로 고정하고, 그 위에 13개 시나리오(A-M)를 얹어 "온톨로지 하나가 얼마나 많은 경험을 구동할 수 있는가"를 30-60분 데모로 보여주는 PoC입니다. 의미 검색과 대화형 에이전트 같은 LLM 시나리오부터, 이탈 위험 진단과 등급 상승 lift 같은 순수 그래프 집계 시나리오까지 같은 그래프를 공유합니다.

데모 전체를 관통하는 장치는 5개의 스파인 페르소나(임산부, 4세 아이 엄마, 캠퍼, 민감성 피부, 글루텐 알레르기)입니다. 40개의 서사형 페르소나(psn_*) 중 라벨 키워드가 스파인과 매칭되는 것(현재 9/40)만 DERIVED_FROM 엣지로 스파인에 연결되며, 나머지는 회원 집합으로 해석되지 않습니다. 시나리오 A부터 M까지 같은 페르소나 컨텍스트가 일관되게 유지되는 것이 이 PoC의 설계 목표 중 하나입니다.

원칙: 시나리오마다 데이터 모델을 새로 만드는 대신, 온톨로지 스키마 하나에 계층(커머스, 물류, 멤버십, 외부 소비)을 누적하며 시나리오를 늘립니다.

02온톨로지 스키마와 합성 데이터

스키마의 단일 기준점은 api/routers/ontology.py의 _CLASSES와 _RELATIONS 레지스트리입니다. 코드 기준으로 노드 클래스는 25종, 관계는 40종입니다. 클래스는 도메인 필드로 계층화되어 있습니다.

  • core / standards - Product, Brand, Manufacturer, Category, Ingredient, Nutrient. 성분과 카테고리는 INCI, FoodOn(한글 별칭 219건), GS1과 KFDA 매핑 CSV(ontology/mappings/)로 외부 표준에 연결됩니다.
  • lifestyle / retail / narrative - Concern, Trend, Persona, Channel, Promotion, Review.
  • logistics / events - Region, Warehouse, Carrier, Route, Shipment, Inventory, Event. 재고를 엣지 속성이 아닌 일급 노드로 두어 openCypher 순회와 검증을 단순하게 유지합니다.
  • membership - Member, MembershipTier, Campaign, Transaction, Touchpoint.
  • external - IndustryCategory. 외부 소비 패널을 내부 카테고리에 OVERLAPS_WITH로 연결하는 시나리오 M의 축입니다.
참고 - 문서와 코드가 어긋나는 지점

docs/architecture.md는 노드 클래스를 19종으로 기술하지만, 멤버십 5종과 IndustryCategory가 추가된 뒤 코드의 _CLASSES는 25종입니다. README의 시나리오 B 설명도 도구 4개로 남아 있으나 코드의 TOOL_SPECS는 7개입니다. 이 문서의 수치는 전부 코드/데이터 기준입니다.

03AWS 아키텍처 - 여섯 개의 CDK 스택

인프라는 AWS CDK v2(TypeScript)의 스택 6개(network, data, compute, ai, edge, observability)로 정의되고, 스택별 Jest 스냅샷 테스트가 드리프트를 감지합니다. 리전은 ap-northeast-2이고 컴퓨트는 전부 ECS Fargate ARM64입니다.

요청 경로의 특징은 인증과 원본 보호가 애플리케이션 바깥에 있다는 점입니다. CloudFront의 Lambda@Edge가 모든 요청에서 쿠키를 검사해 미인증 사용자를 Cognito Hosted UI로 302시키고, ALB는 CloudFront 전용 prefix list로 잠긴 보안 그룹으로만 열리며, Secrets Manager 기반 X-Origin-Auth-Token 헤더는 API 미들웨어가 검증합니다. API 서비스는 FastAPI + uvicorn 2 replica이며, 같은 컨테이너 이미지가 커맨드 오버라이드로 일회성 데이터 로더 역할도 겸합니다.

데이터 계층은 역할이 분리되어 있습니다. Neptune이 온톨로지 그래프(openCypher, IAM SigV4 인증), OpenSearch Serverless가 하이브리드 검색 인덱스를 맡고, Aurora PostgreSQL Serverless v2는 세션 메타데이터 용도로 프로비저닝되어 있으나 현재 API 코드는 접속하지 않습니다(드라이버 미포함). AI 계층은 Bedrock의 Sonnet 4.6(채팅/인사이트), Cohere embed-v4(1,536차원 임베딩), Cohere rerank-v3(재정렬), Guardrails(입출력 스크럽), Knowledge Base(관리형 RAG)에 AgentCore Memory가 더해집니다(Code Interpreter는 래퍼만 있고 insights 경로에는 아직 배선되지 않았습니다).

주의 - Neptune은 프라이빗 서브넷에만 있습니다

개발용 EC2에서 Neptune 엔드포인트에 직접 접속할 수 없습니다. 합성 데이터 적재는 같은 보안 그룹을 쓰는 일회성 ECS 태스크(aws ecs run-task + 커맨드 오버라이드)로만 가능합니다. 로컬에서 로더를 돌리려다 타임아웃을 만나는 것이 이 저장소에서 가장 흔한 함정입니다.

04핵심 메커니즘 딥다이브

4.1 하이브리드 검색과 rerank 폴백

시나리오 A의 검색은 api/services/search.py에 있습니다. 한국어 쿼리를 Nori 분석기의 BM25와 Cohere embed-v4의 KNN으로 각각 검색한 뒤, 애플리케이션 단에서 Reciprocal Rank Fusion으로 병합합니다. 코드 주석이 밝히듯 k=60은 RRF 원 논문의 표준 튜닝값이고, 두 검색을 분리 실행 후 융합하는 방식이 네이티브 하이브리드에 근접한 품질을 냅니다. 융합 결과는 rerank-v3 cross-region inference profile로 재정렬되는데, 이 단계는 어떤 오류에서도 RRF 순서로 조용히 폴백하도록 설계되어 있습니다.

api/services/search.py - RRF 융합과 rerank 폴백
hits_raw = _rrf_merge(knn_raw, bm25_raw, k=60)
# ... SearchHit 후보 구성 ...
if not rerank or not settings.bedrock_reranker_inference_profile_arn or not candidates:
    return candidates[:top_k]
try:
    return _bedrock_rerank(scrubbed, candidates, top_k)
except Exception:
    return candidates[:top_k]   # rerank 실패 시 RRF 순서 유지

또 하나의 설계 결정은 Guardrails 스크럽이 rerank보다 앞에 있다는 점입니다. 쿼리는 재정렬 모델에 전달되기 전에 PII가 제거된 scrubbed 형태가 됩니다. 검색 결과는 1-hop 지식 부분그래프와 함께 시각화되어, 왜 이 상품이 나왔는지를 관계로 설명합니다.

4.2 멀티턴 에이전트와 AgentCore Memory

시나리오 B의 에이전트(api/services/agent.py)는 Bedrock Converse의 도구 호출 루프입니다. TOOL_SPECS에 등록된 도구는 7개입니다 - semantic_search, kb_lookup, neptune_subgraph, memory_recall에 물류 3종(nearest_warehouses haversine k-NN, shortest_path BFS, inventory_lookup)이 더해진 구성입니다. 모든 스트리밍 엔드포인트는 phase/delta에 종결 이벤트(stop 또는 result)를 더한 공통 SSE 어휘를 쓰고, 도구 호출 log 이벤트는 에이전트 스트림에만 있어 프론트엔드의 실시간 도구 호출 패널에 나타납니다.

메모리는 AgentCore Memory 하나로 단기와 장기를 모두 처리합니다. 단기는 세션 단위 이벤트 저장이고, 장기는 user/{actor_id}/preferences 네임스페이스에 사용자별 사실을 7일 TTL로 보관합니다. 대화 시작 시 memory_recall이 장기 메모리에서 페르소나 관련 사실을 회수해 시스템 컨텍스트에 주입하므로, 세션이 바뀌어도 "지난번에 임산부용을 찾았다"는 맥락이 이어집니다. 입력과 출력 양쪽에 Guardrails 검사가 phase 이벤트로 노출됩니다.

시나리오 C는 Neptune 트렌드 집계를 Sonnet 4.6이 한국어로 스트리밍 요약하는 구성입니다(에이전트 도구 루프가 아닌 단순 converse_stream 호출입니다). Code Interpreter 래퍼(api/services/code_interpreter.py)는 존재하지만 insights 엔드포인트에 아직 배선되지 않았고(프론트 문구도 "Phase 4 wiring"), 실제 차트는 API가 반환한 chart_spec JSON을 프론트엔드가 렌더링합니다.

4.3 그래프 순회 시나리오의 대표 패턴

LLM이 개입하지 않는 시나리오들(D, I, J, K, L, M)은 openCypher 순회와 집계의 변주입니다. 13개를 나열하는 대신 반복해서 등장하는 패턴 세 가지를 봅니다.

패턴 1 - 페르소나 스파인 OR 브릿지. 모든 회원 시나리오는 같은 Cypher 조각으로 페르소나 필터를 겁니다. 회원이 스파인 페르소나에 직접 매칭되거나, 서사형 페르소나를 거쳐 DERIVED_FROM으로 스파인에 닿거나 - 두 경로를 OR로 묶는 것이 핵심입니다.

api/routers/vip.py - _persona_filter_fragment (ADR-0006)
f"{where_keyword} ((m)-[:MATCHES_PERSONA]->(:Persona {{persona_id: $pid}}) "
"  OR (m)-[:MATCHES_PERSONA]->(:Persona)<-[:DERIVED_FROM]-(:Persona {{persona_id: $pid}})) "

패턴 2 - 그래프 사이드 사전 계산과 코호트 lift. 시나리오 I의 churn_risk는 API가 실시간 계산하지 않습니다. 합성 데이터 생성기가 RFM으로 계산해 Member 노드 속성으로 심어 두고, 라우터는 등급과 페르소나 축으로 집계만 합니다. 시나리오 K의 Silver에서 Gold 상승 lift는 상품별 Gold 구매율을 Silver 구매율로 나눈 per-capita 비율인데, 분자가 0인 코호트에 half-step smoothing(1 / silver_n / 2)을 적용해 0 나눗셈을 피합니다.

패턴 3 - 브릿지 엣지로 외부 데이터 접합. 시나리오 M은 외부 소비 패널을 별도 시스템으로 두지 않고, HAS_CATEGORY_SPEND 엣지 10,410건과 OVERLAPS_WITH 브릿지 43건으로 기존 그래프에 이어 붙입니다. 덕분에 "내부 지갑 점유율이 낮은데 외부 총지출이 큰 회원"(Opportunity) 같은 5축 VIP 정의가 전부 단일 그래프 질의로 표현되고, 패턴 1의 페르소나 필터도 그대로 재사용됩니다.

표에서 읽어야 할 것은 개별 시나리오의 화려함이 아니라 재사용 구조입니다. A와 B가 검색 스택을, H와 I와 K와 L이 한국 시도 코로플레스 컴포넌트를, I, K, L, M이 페르소나 스파인 필터를 공유합니다(J는 TARGETS 기반 페르소나 x 채널 매트릭스입니다). 시나리오가 13개여도 기반 메커니즘은 4절에서 본 세 패턴과 검색/에이전트 스택의 조합으로 수렴합니다.

06메타 페이지 /codegraph - 코드베이스 자체의 지식그래프

이 저장소는 "온톨로지로 도메인을 그린다"는 주제를 자기 자신에게도 적용합니다. /codegraph 페이지는 graphify가 소스 코드 AST에서 추출한 그래프를 임베드하는데, web/public/codegraph/graph.json을 직접 세어 보면 노드 1,751개 / 엣지 2,217개 / 커뮤니티 159개이고 소스 파일 150개가 대상입니다. GRAPH_REPORT 기준으로 엣지의 97%가 AST에서 직접 추출(EXTRACTED)되었고 빌드 시점 LLM 호출은 0회입니다.

LLM은 빌드가 아니라 라벨링 단계에만 개입합니다. scripts/label_codegraph_communities.py가 커뮤니티 159개 각각에 대해 Bedrock Sonnet 4.6을 호출해 4개 필드(label, description, key_concepts, top_files)의 구조화 JSON을 받고, graph.html을 in-place 패치해 "Community 42" 같은 ID를 의미 있는 한국어 라벨로 바꿉니다. 전체 갱신은 ./scripts/refresh_codegraph.sh 한 번으로 끝나며 Bedrock 호출 159회를 포함해 약 3분이 걸립니다.

결정적 구조(AST 추출)와 확률적 해석(LLM 라벨링)을 분리한 이 구성은 본편 시나리오들과 같은 철학입니다. 그래프가 사실을 들고 있고, LLM은 그 위에서 읽기 좋은 층을 덧씌웁니다.

07한계와 결론

7.1 한계

  • 데이터가 전부 합성입니다. 페르소나 편향과 성장 계수까지 생성기가 심은 값이므로, 이탈 위험 분포나 VIP 축의 크기 같은 결과를 실제 리테일 데이터의 성질로 일반화할 수 없습니다.
  • 보안이 데모 태세입니다. ALB 오리진은 HTTP-80(TLS는 CloudFront에서 종료)이고 Cognito 패스워드 정책도 데모 수준입니다. SECURITY.md가 프로덕션 전환 계획을 명시하고 있으나 현재 코드는 그 이전 상태입니다.
  • Neptune은 단일 인스턴스 dev 사이징이고, rerank-v3는 cross-region inference profile이 없는 리전/계정에서는 비활성입니다(이때 검색 품질은 RRF 순서로 떨어집니다).
  • 문서-코드 드리프트가 존재합니다. 2절의 클래스 수와 도구 수 불일치가 그 예로, 저장소를 읽을 때는 ontology.py와 agent.py 같은 레지스트리 코드를 기준으로 삼아야 합니다.

7.2 결론

이 PoC의 가치는 개별 기능이 아니라 결합 패턴의 카탈로그라는 데 있습니다. 온톨로지 스키마를 단일 기준점으로 두고 계층을 누적하는 방법, RRF 융합에 rerank를 폴백 가능한 선택 단계로 얹는 방법, Converse 도구 루프에 그래프 순회와 메모리 회상을 도구로 등록하는 방법, 브릿지 엣지로 외부 데이터를 접합하는 방법이 모두 동작하는 코드로 남아 있습니다. 한국 리테일/CPG 도메인에서 지식그래프와 관리형 AI 서비스의 결합을 검토한다면, 이 저장소는 아키텍처 결정(ADR)과 함께 출발점으로 삼을 만합니다.

결론: 온톨로지는 시나리오를 늘릴수록 비용이 줄어드는 자산이며, 이 PoC는 그 손익분기점이 13개 시나리오 안에서 이미 지나갔음을 코드로 보여줍니다.
