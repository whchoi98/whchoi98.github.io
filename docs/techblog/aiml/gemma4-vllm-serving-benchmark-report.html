요약

  • 기존 GPU인 L40S(g6e.2xlarge)에서 S1 채팅 처리량은 최대 536 tok/s입니다. 같은 작업을 신형 g7e(RTX PRO 6000 Blackwell)로 옮기면 1,871 tok/s가 되고, 네 시나리오 전부에서 3.49배에서 4.83배 높습니다.
  • g7e의 우위는 4비트 연산(FP4)을 하드웨어가 직접 처리하는 커널과 96GB GDDR7 메모리에서 나옵니다. 문맥 저장 공간인 KV 캐시가 125,023 tokens까지 확보되어, L40S가 포화하던 고동시성 구간의 강제 중단(preemption)이 사라집니다.
  • 합격 기준인 GPU당 처리량 1.5배를 3배에서 5배까지 상회하며, Spot 가격($1.50/hr)을 반영한 비용 효율은 6배에서 9배입니다. 다만 당근 현행 GPU당 처리량 수치가 아직 입력되지 않아 배율 확정은 그 값 확보 후로 남습니다.
  • 서버 기동은 로더 교체(runai_streamer S3 직결)와 compile 캐시 영속화로 콜드 537초에서 웜 155초로 줄었고, 가중치 로드는 12xlarge NVMe와 g7e에서 19~18초까지 내려갑니다. 한국어 지연은 공식 MTP assistant(수용률 56%)로 2.6배 단축되며, 권장 프로덕션 구성은 별도 절에 정리합니다.

01배경과 판정 기준

이 절은 이번 측정을 왜 했고, 어떤 결과가 나오면 성공으로 볼지 정리합니다. 판정 기준을 먼저 정해 두어야 뒤의 수치를 같은 잣대로 읽을 수 있습니다.

이 PoC의 질문은 하나입니다. Gemma-4-31B를 vLLM으로 서빙할 때 GPU당 처리량이 현행 대비 1.5배 이상 나오는지입니다. vLLM은 대규모 언어 모델을 API 서비스 형태로 돌리는 오픈소스 서빙 엔진입니다.

처리량이 1.5배가 되면 같은 트래픽을 더 적은 서버로 감당할 수 있습니다. 그러면 서빙 레플리카를 12개에서 8개로 줄이는 근거가 됩니다. 판정 대상은 채팅, 요약, 분류, 장문 RAG 네 가지 실사용형 워크로드입니다.

측정은 두 단계로 진행했습니다. 먼저 확보가 쉬운 L40S(g6e) 위에서 기준선을 잡고, 서빙 파이프라인의 병목인 스타트업, 양자화 포맷, 한국어 지연을 정리했습니다. 양자화는 모델 가중치를 낮은 정밀도 숫자로 줄여 메모리와 연산을 아끼는 기법입니다.

그다음 FP4 텐서코어를 네이티브로 갖춘 g7e(RTX PRO 6000 Blackwell)를 Spot으로 확보해 본판정을 냈습니다. Spot은 클라우드의 남는 용량을 할인가에 빌리는 방식입니다.

지표는 네 가지를 봅니다. 처리량은 output tok/s(초당 생성 토큰 수)와 req/s(초당 처리 요청 수)로 잽니다. 지연은 TTFT(첫 토큰이 나올 때까지 걸리는 시간)와 ITL(토큰과 토큰 사이 간격)로 잽니다.

참고 - 판정 기준의 미완 항목

판정식의 분모인 당근 현행 GPU당 처리량 수치는 아직 입력되지 않았습니다. 따라서 이 문서의 배율은 L40S 기준선 대비 g7e의 상대 배율이며, 현행 대비 최종 배율은 그 값이 확보되면 확정됩니다.

02실험 환경과 방법

이 절은 실험을 돌린 장비와 측정 방법을 설명합니다. 뒤에 나오는 모든 수치는 여기서 정한 조건 위에서 읽어야 합니다.

서울 리전 EKS 클러스터(GPU01)의 serving 네임스페이스에 vLLM v0.26.0을 배포했습니다. EKS는 AWS의 관리형 Kubernetes 서비스이고, GPU 노드 확보는 자동 프로비저너인 Karpenter가 맡습니다. 모델 가중치는 S3 버킷에서 runai_streamer로 직접 적재했는데, 이는 가중치 파일을 S3에서 GPU로 병렬 스트리밍하는 vLLM 로더입니다.

NVFP4는 4비트, FP8은 8비트 부동소수점 양자화 포맷입니다. 같은 NVFP4 가중치라도 GPU 세대에 따라 실행 커널이 다릅니다. L40S(SM89)는 FP4 텐서코어가 없어 NVFP4가 Marlin W4A16 커널로 자동 폴백(대체 실행)되고, g7e(Blackwell)는 FlashInferCutlassNvFp4 네이티브로 돕니다. FP8 W8A8은 L40S에서도 Ada FP8 텐서코어로 네이티브 실행이며 폴백이 아닙니다.

03L40S 기준선 28조합

이 절은 기존 세대 GPU인 L40S에서 잰 출발점 수치를 다룹니다. 뒤에서 g7e가 얼마나 빨라졌는지 계산할 때 이 값이 분모가 됩니다.

측정 조건은 nvidia/Gemma-4-31B-IT-NVFP4, 8K 컨텍스트, KV 캐시 31,344 tokens, speculative decoding 끔입니다. KV 캐시는 앞서 처리한 문맥의 중간 계산을 담아 두는 GPU 메모리 영역이고, 이 용량이 동시 처리 한도를 정합니다. speculative decoding은 작은 모델이 미리 추측한 토큰을 본 모델이 한 번에 검증하는 가속 기법인데, 이 라운드에서는 껐습니다.

첫 질문은 각 시나리오가 최대 몇 tok/s까지 나오는가입니다. 표 3에서는 시나리오별 최대 처리량과 그 최대가 나온 동시성 지점을 봅니다.

04스타트업 단축 A/B

이 절은 서버가 켜져서 요청을 받기까지 걸리는 시간, 즉 스타트업을 어디까지 줄일 수 있는지 다룹니다. 새 GPU 노드가 뜰 때마다 반복되는 비용이라 운영에서 체감이 큰 항목입니다.

먼저 콜드 스타트(캐시가 전혀 없는 첫 기동) 537초(8분 57초)를 단계별로 분해했습니다. 가중치 로드 149초, torch.compile 73초, 신규 노드 확보 48초, 이미지 pull 82초입니다. torch.compile은 모델 실행 코드를 첫 기동 때 최적화 컴파일하는 단계입니다.

구성을 바꿔가며 이 병목을 어디까지 줄일 수 있는지 측정했습니다. 측정 구간은 pod 생성부터 /health 200 도달까지이고, 구간 분해는 vLLM 기동 로그 기준입니다(vLLM v0.26.0, 2026-08-05~06 수동 계측).

비교 기준선은 당근 현행 경로입니다. HuggingFace → S3 sync → S3 Mountpoint 위에서 runai_streamer(concurrency 32, memory_limit 8GiB)로 로드하는 구성입니다. Mountpoint는 S3 버킷을 파일시스템처럼 마운트해 주는 FUSE 도구입니다.

이 경로의 기동 시간은 이미 16분에서 5분까지 개선된 상태였습니다. 이번 실측은 같은 경로의 병목을 구간별로 확인하고 구성만 바꿔 재측정한 것입니다.

4.1 구성별 A/B - g6e.2xlarge

어떤 구성이 몇 초를 아끼는지가 질문입니다. 표 5에서는 구성별 총 기동 시간과, 그중 가중치 로드와 torch.compile이 차지하는 몫을 봅니다.

가장 큰 효과는 가중치 로드 경로 교체에서 나왔습니다. Mountpoint FUSE는 149초(실효 1.75Gbps)가 걸렸습니다. 반면 runai_streamer S3 직결은 29초에서 32초(실효 8.2Gbps, concurrency 64, memory_limit 24GiB)로 약 5배 빠릅니다.

compile 캐시를 노드에 영속화하면 재기동 시 컴파일이 73초에서 8.5초로 줄어 55초를 공짜로 회수합니다. 엔진 초기화도 93초에서 25초로 줄어듭니다.

참고 - sleep 모드로 유휴 GPU 반납

sleep 모드는 놀고 있는 서버의 GPU 메모리를 잠시 반납해 두는 vLLM 기능입니다. 유휴 시 /sleep으로 26.8초 만에 GPU 메모리 45.4GB에서 14.7GB로 30GB를 반납하고, 수요가 오면 /wake_up으로 3.6초에 복귀했습니다. 155초 풀 재기동 대비 약 40배 빠른 복귀라, 자동 GPU 할당의 구조적 대안이 됩니다.

4.2 인스턴스 / 스토리지 축 - 12xlarge NVMe와 g7e

같은 runai_streamer 직결이라도 인스턴스와 스토리지에 따라 로드 시간이 더 내려갑니다. 가중치 로드만 보면 Mountpoint 149초 → 2xlarge 직결 29~32초 → 12xlarge 19초 → g7e 18초의 계열입니다. NVMe는 노드에 직접 붙은 고속 로컬 SSD를 말합니다.

  • g6e.12xlarge (100Gbps, NVMe RAID0) - 가중치 로드 19초. FP8과 NVFP4 두 모델(합계 66GB)을 같은 노드에서 동시에 로드하는 중에도 이 값이었고, Mountpoint 대비 7.8배입니다. 콜드 스타트(신규 노드 확보 + 이미지 pull + 로딩)는 2모델 동시 기준 380초였습니다. Karpenter NodePool에 instanceStorePolicy: RAID0 한 줄만 넣으면 인스턴스 스토어 3.8TB가 자동 구성됩니다. runai는 concurrency 128 / memory_limit 64GiB를 사용했습니다.
  • g7e.2xlarge (Spot) - 6절 본판정 환경에서 가중치 로드 18초였습니다. 로딩 구간 분해는 g6e 계열에서만 수행했으므로 g7e는 가중치 로드 단일 값입니다.

4.3 한계

  • 콜드 스타트는 재현 비용이 커서 반복 측정하지 못했습니다. 신규 노드에는 compile 캐시가 없으므로, 최적 구성의 콜드 기동 약 4.5분은 추정치입니다.
  • concurrency 값이 인스턴스와 함께 바뀌어(32 → 64 → 128) 단독 효과를 분리하지 못했습니다.
  • NVMe 프리스테이징 후 로컬 로드, fastsafetensors + GDS, FSx for Lustre, EBS 스냅샷 FSR, S3 Express One Zone은 미측정 대안으로 남아 있습니다.

05후속 실험: FP8, 스케일업, 한국어 draft

이 절은 기준선 이후에 남은 세 가지 질문을 실험으로 확인합니다. 양자화 포맷은 무엇이 나은지, 더 큰 인스턴스가 얼마나 이득인지, 한국어 응답을 빠르게 할 초안(draft) 모델은 무엇인지입니다.

5.1 FP8-dynamic 대 NVFP4

g6e.12xlarge 한 노드에 FP8 pod와 NVFP4 pod를 GPU 격리로 동시에 올려 같은 조건에서 비교했습니다. 결론은 워크로드에 따라 갈립니다. 초저지연 채팅은 NVFP4가, 요약과 RAG 같은 고동시성 종합 워크로드는 FP8에 fp8 KV를 켠 구성이 앞섭니다.

fp8 KV는 KV 캐시 자체도 8비트로 저장해 같은 메모리에 더 긴 문맥을 담는 옵션입니다. 표 6에서는 시나리오와 동시성 조합별로 어느 포맷이 이겼는지를 봅니다.

5.2 g6e.12xlarge 스케일업

더 큰 인스턴스는 로딩을 얼마나 앞당길까가 질문입니다. 100Gbps NIC과 NVMe RAID0를 갖춘 12xlarge에서는 runai_streamer 가중치 로드가 두 모델(66GB)을 동시에 올리는 중에도 19초로 끝났습니다. Mountpoint 149초 대비 7.8배입니다.

설정도 간단합니다. instanceStorePolicy: RAID0 한 줄로 NVMe 3.8TB가 kubelet ephemeral-storage로 자동 구성됩니다.

5.3 한국어 speculative decoding

speculative decoding에서는 작은 draft 모델이 토큰을 미리 추측하고 본 모델이 한 번에 검증합니다. 추측이 검증을 통과하는 비율이 수용률이고, 수용률이 높을수록 응답이 빨라집니다. 당근형 한국어 프롬프트 200개로 draft 모델별 수용률을 측정했습니다.

공식 MTP speculator인 google/gemma-4-31B-it-assistant가 수용률 56%로, 축소 어휘(32K vocab) EAGLE3의 5.6% 대비 10배 높았습니다. MTP는 본 모델에 붙여 여러 토큰을 한 번에 예측하게 하는 공식 초안 모듈입니다. 전체 262K vocab을 그대로 쓰기 때문에 한국어를 커버합니다.

06g7e 본판정

이 절이 이 문서의 본판정입니다. FP4 연산을 하드웨어로 직접 실행하는 신형 g7e에서 같은 벤치마크를 다시 돌려 L40S 기준선과 비교합니다.

Spot으로 확보한 g7e.2xlarge에서 NVFP4를 네이티브 커널로 돌렸습니다. KV 캐시가 125,023 tokens까지 잡히고 가중치 로드는 18초입니다. 동일 워크로드, 동일 8K 컨텍스트로 L40S 기준선과 비교한 결과 전 시나리오에서 3.49배에서 4.83배 높았습니다.

01Background and Success Criteria

This section explains why the measurements were made and what outcome counts as success. Fixing the pass criteria first lets every number that follows be read against the same yardstick.

This PoC asks a single question. Does serving Gemma-4-31B with vLLM deliver 1.5x or more throughput per GPU versus the current setup? vLLM is an open-source serving engine that runs large language models as an API service.

At 1.5x throughput, the same traffic can be handled with fewer servers. That justifies shrinking the serving fleet from 12 replicas to 8. The verdict covers four realistic workloads: chat, summarization, moderation, and long-context RAG.

Measurement proceeded in two stages. First, a baseline was established on L40S (g6e), which is easy to procure, and the serving-pipeline bottlenecks were worked through: startup, quantization format, and Korean latency. Quantization is the technique of storing model weights in lower-precision numbers to save memory and compute.

Then g7e (RTX PRO 6000 Blackwell), which has native FP4 tensor cores, was secured as Spot capacity for the final verdict. Spot means renting the cloud's spare capacity at a discount.

Four metrics are used. Throughput is reported as output tok/s (generated tokens per second) and req/s (requests per second). Latency is reported as TTFT (time until the first token appears) and ITL (the gap between consecutive tokens).

Note - An open item in the success criteria

The denominator of the pass formula, Karrot's current per-GPU throughput, has not been provided yet. The ratios in this document are therefore g7e relative to the L40S baseline; the final ratio against the current production setup will be fixed once that number is available.

Model weights were loaded directly from an S3 bucket with runai_streamer, a vLLM loader that streams weight files from S3 to the GPU in parallel.

04Startup Reduction A/B

This section asks how far startup, the time from launching a server to it accepting requests, can be pushed down. The cost repeats every time a new GPU node comes up, so it is keenly felt in operations.

First, the 537 s (8 min 57 s) cold start (a first boot with no caches at all) was broken into phases. Weight loading takes 149 s, torch.compile 73 s, new-node provisioning 48 s, and image pull 82 s. torch.compile is the phase that optimizes and compiles the model's execution code on first boot.

Configurations were varied to see how far each bottleneck could be pushed down. The measured window runs from pod creation to /health returning 200, and the phase breakdown follows the vLLM startup logs (vLLM v0.26.0, manually instrumented on 2026-08-05 to 06).

The comparison baseline is Karrot's current path: HuggingFace → S3 sync → loading with runai_streamer (concurrency 32, memory_limit 8GiB) on top of S3 Mountpoint. Mountpoint is a FUSE tool that mounts an S3 bucket like a filesystem.

That path's startup time had already improved from 16 minutes to 5. This round verified the bottlenecks of the same path phase by phase and re-measured with only the configuration changed.

4.1 Per-configuration A/B - g6e.2xlarge

The question is which configuration saves how many seconds. Table 5 shows total startup time per configuration and the share taken by weight loading and torch.compile.

The biggest gain came from replacing the weight-loading path. Mountpoint FUSE took 149 s (effective 1.75Gbps). By contrast, runai_streamer direct to S3 took 29 to 32 s (effective 8.2Gbps, concurrency 64, memory_limit 24GiB), about 5x faster.

Persisting the compile cache on the node cuts compilation from 73 s to 8.5 s on restart, reclaiming 55 s for free. Engine initialization also drops from 93 s to 25 s.

Note - Returning idle GPU memory with sleep mode

Sleep mode is a vLLM feature that temporarily hands back the GPU memory of an idle server. When idle, /sleep released 30GB of GPU memory (45.4GB down to 14.7GB) in 26.8 s, and /wake_up restored it in 3.6 s when demand returned. That is roughly 40x faster than the 155 s full restart, making it a structural alternative to automatic GPU allocation.

4.2 Instance / storage axis - 12xlarge NVMe and g7e

Even with the same runai_streamer direct connection, load time keeps dropping with instance and storage. Looking at weight load alone, the series is Mountpoint 149 s → 2xlarge direct 29-32 s → 12xlarge 19 s → g7e 18 s. NVMe means fast local SSDs attached directly to the node.

  • g6e.12xlarge (100Gbps, NVMe RAID0) - weight load 19 s. This held even while loading two models (FP8 and NVFP4, 66GB combined) on the same node at once, 7.8x faster than Mountpoint. Cold start (new node provisioning + image pull + loading) was 380 s with both models. A single instanceStorePolicy: RAID0 line in the Karpenter NodePool auto-configures 3.8TB of instance store. runai used concurrency 128 / memory_limit 64GiB.
  • g7e.2xlarge (Spot) - weight load was 18 s in the Section 6 verdict environment. The load-phase breakdown was performed only on the g6e family, so g7e has a single weight-load value.

4.3 Limitations

  • Cold starts are expensive to reproduce and were not measured repeatedly. A new node has no compile cache, so the best configuration's cold startup of about 4.5 minutes is an estimate.
  • concurrency changed together with the instance (32 → 64 → 128), so its standalone effect could not be isolated.
  • NVMe pre-staging with local load, fastsafetensors + GDS, FSx for Lustre, EBS snapshot FSR, and S3 Express One Zone remain unmeasured alternatives.

05Follow-ups: FP8, Scale-up, Korean Draft

This section answers three questions left open after the baseline. Which quantization format is better, how much does a larger instance help, and which draft model should speed up Korean responses?

5.1 FP8-dynamic vs NVFP4

An FP8 pod and an NVFP4 pod were run side by side on one g6e.12xlarge node with GPU isolation, compared under identical conditions. The conclusion depends on the workload. NVFP4 wins for ultra-low-latency chat, while FP8 with fp8 KV enabled wins for high-concurrency mixed workloads like summarization and RAG.

fp8 KV is an option that stores the KV cache itself in 8 bits, fitting more context into the same memory. Table 6 shows which format won for each scenario and concurrency combination.

Table 6. FP8-dynamic vs NVFP4 (Marlin) throughput comparison (output tok/s)
Scenario / concurrencyFP8 (BF16 KV)FP8 (fp8 KV)NVFP4 (Marlin)Winner
S1_chat / 8129.8-146.4NVFP4
S1_chat / 32321.5-411.1NVFP4
S2_summary / 32112.1201.8195.8FP8 + fp8 KV
S3_moderation / 8, 3270.4 / 95.9-57.3 / 75.8FP8
S4_rag / 3252.2104.592.4FP8 + fp8 KV
Warning - FP8 checkpoints need fp8 KV set explicitly

FP8-dynamic checkpoints ship with kv_cache_scheme set to None, so the KV cache defaults to BF16. The model then underperforms at high concurrency for lack of KV space. Adding --kv-cache-dtype fp8 grows KV capacity from 12,150 to 23,320 tokens, and FP8 overtakes NVFP4 on S2 and S4. Judging FP8 as slow while missing this flag is the most common mistake.

5.2 g6e.12xlarge scale-up

The question is how much a larger instance speeds up loading. On the 12xlarge with a 100Gbps NIC and NVMe RAID0, runai_streamer finished loading weights in 19 s even while bringing up two models (66GB) at once, 7.8x faster than Mountpoint's 149 s.

Setup is simple too. A single instanceStorePolicy: RAID0 line auto-configures 3.8TB of NVMe as kubelet ephemeral-storage.

5.3 Korean speculative decoding

In speculative decoding, a small draft model guesses tokens ahead and the main model verifies them in one pass. The share of guesses that pass verification is the acceptance rate, and higher acceptance means faster responses. Draft-model acceptance was measured with 200 Karrot-style Korean prompts.

The official MTP speculator, google/gemma-4-31B-it-assistant, reached 56% acceptance, 10x higher than the 5.6% of the reduced-vocabulary (32K vocab) EAGLE3. MTP is the official drafting module attached to the main model to predict several tokens at once. It covers Korean because it keeps the full 262K vocabulary.

Table 7 shows acceptance per configuration together with the speed change at concurrency 1 (c1) and 8 (c8). E2E p50 is the median time from request start to response completion.

The MTP assistant improves c1 end-to-end latency from 6.85 s to 2.69 s (2.6x) and c8 throughput from 122.9 to 281.5 tok/s (2.3x). The model is also small at 0.94GB, one fifth of EAGLE3 (4.5GB). The conclusion: for a Korean draft, adopting the official MTP assistant with no extra training is the right answer.

06Final Verdict on g7e

This section is the document's final verdict. The same benchmark was re-run on the newer g7e, which executes FP4 math directly in hardware, and compared against the L40S baseline.

NVFP4 ran on native kernels on a Spot g7e.2xlarge. The KV cache reaches 125,023 tokens and weights load in 18 s. Compared against the L40S baseline on the same workloads and the same 8K context, g7e came out 3.49x to 4.83x higher across every scenario.

Table 8 shows the peak-throughput ratio per scenario, plus the cost-efficiency ratio once hourly price is factored in.

Table 8. g7e vs L40S: peak throughput and cost efficiency
ScenarioL40S peakg7e peakThroughput ratioCost-efficiency ratio
S1_chat536 tok/s1,871 tok/s (14.6 req/s)3.49x6.4x
S2_summary226 tok/s910 tok/s (3.6 req/s)4.03x7.4x
S3_moderation81.7 tok/s395 tok/s (24.7 req/s)4.83x8.9x
S4_rag98.6 tok/s402 tok/s (1.6 req/s)4.08x7.5x

Key point: the g7e advantage widens at high concurrency. Preemption is what happens when the KV cache runs short: an in-flight request is stopped and recomputed. 96GB of GDDR7 holds up to 125,023 KV tokens and removes that preemption in the range where L40S used to saturate.

  • Decode latency ITL p50 halves from 45ms to 25ms at concurrency 1 across all scenarios, the effect of 1.6TB/s GDDR7 bandwidth and native FP4 kernels.
  • Moderation (S3) shows the widest gap at 4.83x. The concurrency 16-to-32 range that thrashed on L40S from KV shortage is fully resolved on g7e at 24.7 req/s.
  • Even in the low-concurrency latency range, g7e leads consistently at a minimum of 1.8x across all combinations.
Note - Assumptions behind the cost-efficiency figures

The cost-efficiency ratio divides peak tok/s by the hourly price and compares the results. g7e uses Spot at $1.50/hr; L40S uses on-demand at $2.76/hr. g7e on-demand is $4.13/hr, so Spot availability is the big variable in cost efficiency.

07Recommended Production Configuration

This section folds the conclusions of the preceding experiments into one command you can apply right away. Sections 4 and 5 show which experiment each option came from.

Combining the follow-up results on the L40S environment, the following configuration captures both overall performance and Korean latency. It puts fp8 KV and the MTP assistant on top of an FP8-dynamic checkpoint. Startup is shortened by runai_streamer and the compile cache.

Recommended serving configuration (vLLM v0.26.0, on L40S)
vllm serve <FP8-dynamic checkpoint> \
  --load-format runai_streamer \
  --model-loader-extra-config '{"concurrency":64,"memory_limit":25769803776}' \
  --kv-cache-dtype fp8 \
  --speculative-config '{"method":"mtp","model":"<gemma-4-31B-it-assistant>","num_speculative_tokens":4}' \
  --tool-call-parser gemma4 --reasoning-parser gemma4 --enable-auto-tool-choice
# Additionally: persist VLLM_CACHE_ROOT (compile cache), Pod Identity (S3 read)

What should this combination deliver? The expected effect is a warm startup of 2 to 3 minutes, Korean response latency cut 2.5x, and prefill throughput of about 1.25x. Once g7e is secured, the same configuration is re-verified with native NVFP4 to re-validate the ratios of Section 6.

08Conclusion and Remaining Work

Finally, the overall results are placed against the pass criteria, along with the items still to be confirmed. To sum up in one sentence: moving to g7e alone brings 3.5x or more throughput and 6x or more cost efficiency, and it resolves the startup-time and Korean-latency problems along the way.

On throughput, g7e is 3.5x to 4.8x over L40S, and 6x to 9x on cost efficiency. It clears the PoC pass bar of 1.5x by a wide margin.

So if Karrot's current GPUs are at L40S level or below, there is room to consider going beyond 12-to-8 replicas, down to around 4. Startup and Korean latency have each moved into practical range as well. Table 9 shows which configuration to pick for each operating situation.

Table 9. Recommended configuration per situation
Operating situationRecommendation
Ultra-low-latency chat firstNVFP4, lowest decode ITL
Mixed workloads such as summarization and RAGFP8 + fp8 KV
Korean latency mattersMTP assistant speculator (56% acceptance)

Three items remain.

  • First, closing the pass formula requires Karrot's current per-GPU throughput number.
  • Second, the interaction sweep of MTP, fp8 KV, and high concurrency (num_speculative_tokens 4 vs 8) is unfinished.
  • Third, TP=2/4 (PCIe) measurements in preparation for 70B-class models are still to be done. TP is tensor parallelism, splitting one model across several GPUs.
