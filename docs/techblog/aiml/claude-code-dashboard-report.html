AIML / Tool Deep Dive

claude-code-dashboard - Claude Code 엔터프라이즈 분석 대시보드의 데이터 파이프라인과 지표 설계

Anthropic Analytics / Compliance API와 S3 아카이브를 결합해 조직의 Claude Code 도입을 참여도, 생산성, 비용, 감사 네 축으로 측정하는 오픈소스 대시보드를 코드 기준으로 분석합니다. 도입 성과 측정을 설계해야 하는 플랫폼 엔지니어와 운영 리드를 위한 문서입니다.

작성 기준일은 2026-08-09입니다.

분석 대상은 claude-code-dashboard v2.0.3(2026-07-28 릴리스, MIT 라이선스)입니다.

핵심 데이터 소스는 /v1/organizations/analytics/*와 /v1/compliance/activities입니다.

주 출처는 GitHub 저장소의 코드와 문서(README.md, docs/metrics-catalog.md, server/, collector/, infra/)입니다.

요약

  • claude-code-dashboard는 Anthropic Analytics / Admin / Compliance API와 Spend Report CSV, S3 아카이브를 하나로 묶어 19개 페이지로 조직의 Claude Code 사용을 보여주는 CloudFront 기반 대시보드입니다.
  • Analytics API는 조회 가능 기간 90일, engagement 3일 버퍼, cost 계열 요청당 31일 상한, 조직 단위 60 rpm 제한이 있어 그대로는 운영 리포팅이 어렵습니다. 이 프로젝트는 Lambda collector가 매일 S3에 NDJSON으로 적재하고 서버가 S3 우선으로 응답해 이 제약을 우회합니다.
  • 생산성은 도구 수락률, 활동 점수, 경제 생산성 점수(v3, 코드 기준 가중치 0.55 / 0.25 / 0.12 / 0.08)로 계량화하고, Bedrock의 Claude Sonnet 4.6이 SELECT 전용 sanitizer를 거친 Athena SQL로 자연어 질의에 답합니다.
  • 도입을 검토한다면 Analytics API 키 하나로 시작할 수 있습니다. Admin / Compliance 키와 CSV는 선택 사항이며 없으면 해당 페이지만 비활성화됩니다. 고정 인프라 비용은 README 추정 기준 월 약 $66에서 $70입니다.

01문제 정의 - 조직 도입에서 무엇을 측정하는가

Claude Code를 팀 단위로 도입하면 "잘 쓰이고 있는가"라는 질문이 곧바로 네 개의 서로 다른 질문으로 갈라집니다. 누가 얼마나 자주 쓰는가(참여도), 무엇을 만들어냈는가(생산성), 얼마를 쓰고 있는가(비용), 그리고 무엇을 했는가(감사)입니다. claude-code-dashboard는 이 네 축에 다섯 번째 축인 "이 데이터가 무엇을 의미하는가"(AI 분석)를 더해 하나의 대시보드로 통합합니다.

Anthropic은 이 질문들에 답할 원천 데이터를 API로 제공하지만, 축마다 소스가 다릅니다. 참여도와 Claude Code 생산성은 Analytics API의 engagement 계열이, 비용은 같은 키의 cost 계열 4개 엔드포인트가, 감사 이벤트는 Compliance API가 담당합니다. 어느 소스에도 다른 축의 데이터가 없어서, 예를 들어 "사용자별 지출 대비 산출"을 보려면 두 소스를 이메일로 조인해야 합니다.

표 1. 측정 축과 데이터 소스 (docs/metrics-catalog.md 기준)
측정 축소스대표 데이터
참여도Analytics /summaries, /usersDAU/WAU/MAU, 좌석 수, 도입률
생산성Analytics /users의 claude_code_metricsLOC 추가/삭제, 커밋, PR, 도구별 수락/거절

해석Amazon Bedrock + Athena 아카이브자연어 질의에 대한 Markdown 분석 리포트

두 번째 문제는 조회창 제한입니다. Analytics API는 조회 가능 기간이 90일이고, engagement 계열은 오늘부터 3일 이내 날짜를 조회할 수 없으며(3일 버퍼), cost 계열은 요청당 최대 31일 범위만 허용합니다. rate limit은 키가 아니라 조직 단위로 60 rpm이라 뷰어 여러 명이 동시에 접속하면 예산을 나눠 씁니다. 분기 단위 리포팅이나 연간 추세 분석은 API를 직접 호출하는 방식으로는 불가능하고, 이것이 이 프로젝트가 S3 아카이브 계층을 두는 이유입니다.

원칙: 이 대시보드의 설계 문제는 "차트를 그리는 것"이 아니라, 소스가 갈라져 있고 조회창이 제한된 API들을 조인 가능하고 보존 가능한 형태로 재구성하는 것입니다.

02동작 원리 - 데이터 파이프라인

전체 구조는 3계층입니다. 브라우저의 React SPA(React 18 + Vite 5 + TypeScript 5, Recharts 2), ECS Fargate에서 도는 Express 4 프록시, 그리고 90일 API 조회창 너머의 보존을 담당하는 S3 + Glue + Athena 아카이브입니다. CloudFront와 WAF가 ALB 앞을 막고, ALB 보안 그룹은 CloudFront 관리형 prefix list로 잠겨 있어 직접 접근이 차단됩니다.

2.1 수집 - collector Lambda

Node 20 Lambda(collector/handler.js)가 EventBridge 스케줄로 매일 실행되어 Analytics API의 5개 engagement 엔드포인트(users, summaries, skills, connectors, projects)와 Compliance 감사 피드를 스냅샷합니다. 결과는 s3://<bucket>/<table>/date=YYYY-MM-DD/ 형태의 NDJSON 파티션으로 쓰이고, Glue Data Catalog의 테이블 6종(claude_code_analytics, summaries_daily, skills_daily, connectors_daily, projects_daily, compliance_daily)이 파티션 프로젝션으로 이를 읽습니다. 평탄화 매핑이 아직 다루지 않는 API 필드를 나중에 복구할 수 있도록 원본 레코드 사이드카를 raw/<table>/ 아래에 함께 남기는 점이 특징입니다.

2.2 서빙 - Express 프록시의 S3 우선 전략

기간 조회(/api/analytics/users/range 등)는 S3 아카이브를 먼저 읽고, 캐시 미스가 난 날짜만 실 API로 나갑니다. README는 S3 히트 시 응답을 약 150 ms로 서술합니다. 응답에는 {"s3_hits": 14, "live_calls": 0} 형태의 캐시 힌트가 실려서 아카이브 최신성을 바로 진단할 수 있습니다. 서버에는 10분 in-memory 캐시와 stale-while-revalidate 방식의 비용 캐시, 그리고 UI 프리셋 창을 미리 데우는 keep-warm 스케줄러가 있어 조직 단위 60 rpm 예산 안에서 다중 뷰어를 감당합니다.

cost 계열의 요청당 31일 상한은 서버가 흡수합니다. splitCostWindow()(server/aws.js)가 긴 창을 31일 이하 청크 최대 6개로 쪼개 병합하므로, 대시보드는 한 번의 질의로 최대 186일 창까지 정확한 합산을 보여줍니다. 그 이상은 최근 구간으로 클램프하고 배너로 알립니다.

2.3 표시 - React SPA

프론트는 19개 라우트, 영어/한국어 런타임 토글, 7일 기본 날짜 범위 컨트롤, 사용자 행 클릭 시 열리는 드릴다운 패널로 구성됩니다. Analyze, Cost, Executive 페이지는 print CSS 기반의 PDF 내보내기를 지원합니다.

참고 - 세 API 키는 모두 선택적 결합입니다

Analytics, Admin, Compliance 키는 각각 별도의 Secrets Manager 시크릿(ccd/analytics-key 등)으로 주입되고, 없는 키에 해당하는 페이지만 조용히 비활성화됩니다. Analytics 키 하나만으로 참여도와 생산성 페이지가 동작하고, CLAUDE.md에 따르면 현재는 Analytics 키의 scope가 compliance 읽기까지 커버해 전용 Compliance 키 없이도 서버가 자동 폴백합니다.

03핵심 지표와 산식

이 대시보드가 계산하는 파생 지표는 docs/metrics-catalog.md에 공식과 함께 문서화되어 있습니다. 여기서는 의사결정에 직접 쓰이는 대표 지표 네 가지를 코드 기준으로 살펴봅니다.

3.1 도구 수락률 (Tool Acceptance Rate)

가장 기본이 되는 품질 지표입니다. Claude Code의 편집 도구 4종(edit, multi_edit, write, notebook_edit)이 낸 제안 중 사용자가 수락한 비율로, accepted / (accepted + rejected)로 계산합니다. AI 제안 품질과 사용자 신뢰도가 결합된 지표이며, 분모가 0이면 null로 두어 "데이터 없음"과 "0%"를 구분합니다.

3.2 활동 점수 (User Activity Score)

비용 데이터 없이 Analytics만으로 사용자별 랭킹을 만드는 점수입니다. 다섯 항목의 가중합으로, 각 항목은 목표치 대비 정규화 후 0에서 1로 클램프됩니다.

docs/metrics-catalog.md 4.5 - User Activity Score (0-100)
score = 0.30 ·N(LOC_added_per_day / 200)
      + 0.25 ·user_acceptance_rate
      + 0.20 ·N(commits_per_day / 1.5)
      + 0.15 ·N(active_day_share / 0.4)
      + 0.10 ·N(sessions_per_day / 3)    # N(x) = [0,1] 클램프

3.3 경제 생산성 점수 (Cost-Efficiency Score v3)

사용자별 지출(cost 계열)과 산출(Analytics)을 이메일로 조인해 "달러당 산출"을 순위화하는 점수입니다. 코드(server/aws.js의 scoreEconomicProductivity())는 표면별 산출(code, cowork, office, design)을 각 표면의 활성 사용자 집단 안에서 winsorize 후 중앙값 앵커로 정규화하고, 활성 표면 평균을 지출로 나눈 값을 다시 집단 내 정규화해 value 항을 만듭니다.

server/aws.js - ECON_V3_DEFAULTS (v3 가중치, 코드 기준)
weights: { value: 0.55, acceptance: 0.25, delivery: 0.12, breadth: 0.08 }
churnDiscount: 0.5   // code_raw = loc_added - 0.5 * loc_removed
deliveryIdeal: 2.0   // delivery = (commits+prs)/active_days / 2.0
참고 - 문서와 코드가 어긋나는 지점

docs/metrics-catalog.md 4.4절에는 이전 버전 공식(가중치 0.35 / 0.20 / 0.20 / 0.15 / 0.10)이 남아 있습니다. 실제 배포 코드와 README는 모두 v3(0.55 / 0.25 / 0.12 / 0.08)이며, 본 문서는 코드를 기준으로 서술합니다.

3.4 프롬프트당 작업 수 (Actions per Prompt)

Agentic 페이지의 위임도 지표입니다. Cowork가 action_count와 message_count를 모두 제공하는 유일한 표면이라 Cowork 기준으로 sum(action_count) / sum(message_count)를 계산하고, Claude Code는 프롬프트 수 필드가 없어 세션당 수락된 작업 수를 프록시로 씁니다. 값이 높을수록 팀이 한 번의 지시로 더 많은 작업을 위임한다는 뜻입니다.

주의 - LOC는 순증가가 아닙니다

Analytics의 lines_of_code.added_count는 세션 안에서 같은 코드를 쓰고 지우기를 반복해도 계속 누적됩니다. 코드의 v3 점수가 added - 0.5 * removed로 churn을 할인하는 이유가 이것이며, LOC 단독 랭킹을 성과 평가에 그대로 쓰면 안 됩니다.
