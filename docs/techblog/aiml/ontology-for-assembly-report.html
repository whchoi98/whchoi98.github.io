국회 OpenAPI 위의 언론사 Agentic AI 지식그래프: ontology-for-assembly 아키텍처 분석

실제 국회 열린데이터광장 공공 데이터를 31개 클래스 온톨로지로 적재하고, 그 위에서 23개 Agentic AI 시나리오를 시연하는 PoC 저장소를 코드 기준으로 분석합니다. 공공 데이터 기반 지식그래프와 다중 에이전트 설계를 검토하는 엔지니어를 위한 문서입니다.

작성 기준일은 2026-08-09입니다.

적용 대상은 공공 데이터 기반 Agentic AI 지식그래프 PoC를 설계하는 아키텍트와 엔지니어입니다.

분석 대상 저장소는 whchoi98/ontology-for-assembly입니다.

주 출처는 저장소의 README, CLAUDE.md, CHANGELOG, docs/, 코드(2026-08-09 로컬 체크아웃)입니다.

요약

  • ontology-for-assembly는 국회 열린데이터광장 OpenAPI의 실 데이터(22대 의원 286명, 약 74,000개 그래프 엣지)를 31개 클래스 온톨로지로 Neptune에 적재하고, 23개 시나리오와 6개 페르소나를 30-60분에 시연하는 언론사 Agentic AI PoC입니다.
  • 모든 그래프 노드는 Pydantic base 클래스에서 source ∈ {real, synthetic, external} 필드를 강제 받아, 실 데이터와 합성 데이터가 UI 출처 배지(DataSourceBadge)로 항상 구분됩니다.
  • 차별점은 두 가지입니다. 같은 질문을 Chatbot(RAG), Agent(Tool Use), Agentic AI(Planner-Graph-Analyst-Editor 4 에이전트)로 나란히 비교하는 3단계 진화 비교와, Agent 모드만 민감 콘텐츠에서 광고 노출을 생략하고 근거를 AdMatchDecision 노드에 남기는 광고 매칭 거버넌스입니다.
  • 정치라는 민감 도메인을 다루기 위해 ADR-0004가 6개 레이어의 중립성 가드레일(Bedrock Guardrails, 프롬프트 suffix, balance score, 필드 저장 금지, 사전 검증 질문 풀, 광고 거버넌스)을 정의하며, 이 패턴은 다른 민감 도메인 PoC에 그대로 재사용할 수 있습니다.

01문제 정의: 공공 데이터 위의 뉴스룸 Agentic AI

이 프로젝트가 푸는 문제는 "한국 언론사가 국회 공공 데이터를 실제 업무 도구로 쓸 수 있는가"입니다. 국회 열린데이터광장(open.assembly.go.kr)은 의안, 의원, 표결, 위원회, 정당 데이터를 OpenAPI로 공개하지만, 원천 데이터만으로는 편집국의 취재 판단, 독자 서비스, 정책 인텔리전스 같은 뉴스룸 업무와 연결되지 않습니다. ontology-for-assembly는 이 간극을 지식그래프 + Agentic AI 조합으로 메우는 30-60분 PoC 데모입니다.

설계 스펙(docs/superpowers/specs/2026-05-13-ontology-assembly-design.md)이 명시한 목표는 세 가지입니다. 편집국 생산성(내부), 독자 서비스 차별화(B2C), 정책 인텔리전스(B2B)를 하나의 데이터 기반 위에서 동시에 시연하는 것입니다. 그래서 페르소나가 내부 3개(편집국, 데이터/AI, 광고/세일즈)와 대고객 3개(일반 독자, 유료 구독자, 기업/B2B 정책 인텔리전스)로 나뉘어 있고, 같은 그래프를 페르소나마다 다른 KPI 가중치와 어조로 봅니다. 페르소나 정의의 단일 진실원은 api/services/persona.py:PERSONA_REGISTRY이며 6개 항목이 등록되어 있습니다.

저장소는 자매 프로젝트 ontology-for-gcc(plan1-foundation 브랜치)를 차용 베이스로 삼았습니다. README와 CLAUDE.md 모두 디렉토리 구조, 6-stack CDK, 프로젝트 하니스를 그대로 가져오고 도메인만 국회/언론으로 교체했다고 명시합니다. 이 문서는 차용된 골격이 아니라 이 프로젝트만의 차별점, 즉 실제 국회 OpenAPI 데이터, 3단계 진화 비교, 광고 매칭 거버넌스, 출처 프로버넌스 배지를 중심으로 분석합니다.

핵심: 이 PoC의 주제는 모델 성능이 아니라, 민감한 공공 데이터를 다루는 Agentic AI에 출처 투명성과 거버넌스를 코드 레벨에서 강제하는 방법입니다.

2.2 데이터 코호트: real / synthetic / external 출처 태깅

이 프로젝트의 두드러진 설계는 데이터 출처를 스키마 레벨에서 강제한다는 점입니다. 모든 노드의 base 클래스가 source 필드를 필수로 요구하고, extra="forbid"로 미정의 속성(예: 정치 성향 추론 필드)의 저장 자체를 차단합니다.

data/schemas.py - 모든 Neptune 노드의 base 클래스
class GraphNode(BaseModel):
    # `source` 필드 필수 - DataSourceBadge UI 노출에 사용
    # `extra="forbid"` - 정치 성향 추론 필드 등 미정의 속성 차단
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    source: Source    # "real" | "synthetic" | "external"

세 코호트는 어댑터 디렉토리로도 분리되어 있습니다. data/real/은 국회 OpenAPI 어댑터 (bill, member, vote, committee, session, party, agency)로 22대 의원 286명(members_22.json)을 포함한 실 데이터를 가져오고, data/synthetic/은 독자, 광고, 기사, 토픽을 합성 생성하며, data/external/은 네이버 뉴스와 여론조사 ETL을 담당합니다. 페르소나와 시나리오 조합에 따라 어느 코호트를 조회할지는 api/services/cohort.py가 단일 지점에서 결정하고, Cypher WHERE 절(n.source IN [...])로 변환합니다. 프론트엔드에서는 web/components/DataSourceBadge.tsx가 모든 화면에 출처 배지를 그려, 시연 중 어떤 결과가 실 데이터이고 어떤 결과가 합성인지 즉시 구분됩니다.

2.3 아키텍처

인프라는 AWS CDK v2의 6개 스택(infra-cdk/bin/assembly.ts 기준 network, data, ai, compute, edge, observability)으로 배포됩니다. FastAPI 백엔드(21개 라우터)와 Next.js 14 프론트엔드가 ECS Fargate ARM64에서 돌고, CloudFront와 Lambda@Edge JWT가 앞단을 막습니다. 그래프는 Neptune openCypher, 검색은 OpenSearch Serverless의 Nori BM25 + Cohere KNN 하이브리드(RRF 융합 후 rerank-v3), LLM 계층은 Bedrock Sonnet 4.6과 AgentCore Memory / Code Interpreter입니다. B2B 페르소나는 별도로 API Gateway Usage Plan + API Key 경로를 탑니다.

03딥다이브 1: 3단계 진화 비교 (Chatbot vs Agent vs Agentic AI)

시나리오 B는 이 데모의 첫 번째 메인 메시지입니다. 같은 질문을 세 가지 모드로 동시에 실행해 한 화면에서 나란히 비교합니다. 모드 분기는 api/services/three_stage.py가 담당하고, 세 번째 모드의 다중 에이전트 파이프라인은 api/services/multi_agent.py:run_agentic_pipeline이 실행합니다.

표 2. 3단계 진화 비교 (api/services/three_stage.py, multi_agent.py 기준)
단계방식실행 흐름한계 시연 포인트
Stage 1 Chatbot RAG OpenSearch top-K 검색 결과를 컨텍스트로 Bedrock 1회 호출 검색된 문서 밖의 질문에 답하지 못함
Stage 2 Agent Tool Use search_bills, get_proposers, cosponsor_network, analyze_votes 등 사전 정의 도구를 질문 의도에 따라 순차 호출 도구 목록 안에서만 행동, 계획 수립 없음
Stage 3 Agentic AI 다중 에이전트 Planner(과제 분해) → Graph(Cypher 변환과 Neptune 조회) → Analyst(해석과 가설) → Editor(기사 초안과 후속 취재 포인트) 에이전트 간 재질의를 포함한 자율 협업

4개 에이전트의 역할 프롬프트는 multi_agent.py:AGENT_PROMPTS에 상수로 정의되어 있으며, Analyst는 필요 시 "Graph 에이전트에 재질의 필요"라는 형식으로 그래프 단계에 되물을 수 있습니다. 모든 LLM 호출은 api/services/bedrock.py:invoke()/invoke_stream() 단일 진입점을 거치고, AWS 자격증명이 없으면 결정적 demo mock으로 폴백합니다. 이 폴백 덕분에 오프라인에서도 데모와 테스트가 재현됩니다. 스트리밍은 SSE로 통일되어 있고 이벤트 어휘(phase|delta|log|result|error|done)는 api/routers/chat.py docstring이 단일 진실원입니다.

주의 - Stage 2의 Tool Use는 아직 시뮬레이션입니다

three_stage.py:stage2_agent의 docstring은 "실 Bedrock Converse tool use API 통합은 Phase 2"라고 명시합니다. 현재 코드는 질문 의도를 규칙 기반으로 판별해 도구를 순차 호출하는 흐름을 재현하는 것이며, LLM이 도구 선택을 스스로 하는 실 Converse 통합은 계획 단계입니다. 이 코드를 참조 구현으로 가져갈 때 혼동하기 쉬운 지점입니다.

04딥다이브 2: AI 거버넌스, 광고 매칭 3-way와 중립성 가드레일

4.1 광고 매칭 매트릭스 (시나리오 L)

두 번째 메인 메시지는 광고 매칭 거버넌스입니다. api/services/ad_matcher.py는 같은 기사와 같은 후보 광고 풀에 대해 세 가지 매칭 모드를 실행하고(compare_modes()), 결정 차이를 비교해 보여줍니다.

표 3. 광고 매칭 3-way 비교 (api/services/ad_matcher.py 기준)
모드판단 근거민감 콘텐츠 처리
keyword 토픽-카테고리 단순 매핑, 점수 0.3~0.5 수준 감지 불가, 정치인 비위 기사에도 광고 매칭
embedding 임베딩 코사인 유사도(실 환경 Cohere embed-v4, mock은 결정적 해시 벡터) + avoid_topics 감점 의미 유사성은 잡지만 윤리, 평판 판단 불가
agent 민감 패턴 감지 + avoid_topics 엄격 적용 + 카테고리 점수 민감 콘텐츠 감지 시 chosen_ad_id=None으로 광고 노출 자체를 생략

agent 모드가 광고를 생략할 때 그 근거 문장(reasoning trace)은 AdMatchDecision 노드에 저장되어 운영 콘솔에서 추적됩니다. 즉 "왜 이 지면에 광고가 안 나갔는가"가 그래프에 기록으로 남습니다. 매칭 실행은 API 응답과 분리된 별도 Ad Matcher Lambda로 동작하며, 모드는 AD_MATCH_MODE 환경 변수와 UI 토글로 전환합니다. 데모 샘플 기사는 Agent가 거절해야 하는 3종(scandal, tragedy, minor_victim)과 안전 매칭 3종으로 총 6개가 준비되어 있습니다.

참고 - 민감 패턴은 README 서술(3종)보다 코드가 1종 많습니다

README와 CLAUDE.md는 자동 광고 생략 대상을 비극, 정치인 비위, 미성년 피해자 3종으로 서술하지만, 코드의 SENSITIVE_PATTERNS에는 controversy(폭로, 의혹, 논란)를 포함해 4종의 정규식 패턴이 정의되어 있습니다. 이 문서는 코드 기준으로 4종으로 봅니다.

4.2 정치 중립성 가드레일 6개 레이어 (ADR-0004)

정치 데이터를 다루는 만큼 중립성은 데모 가능성의 전제 조건으로 취급됩니다. ADR-0004(docs/decisions/0004)는 다층 방어 6개 레이어를 정의합니다.

  1. Layer 1 - Bedrock Guardrails 리소스. 정당명 + 비방 조합, 정치인 모욕을 차단하고 시나리오 B, C, I, K의 입력과 출력 양방향에 적용됩니다.
  2. Layer 2 - 모든 LLM 호출에 자동 첨부되는 중립성 system prompt suffix(NEUTRALITY_GUARD_SUFFIX).
  3. Layer 3 - 응답마다 자동 계산되는 political_balance_score. 한쪽 정당만 부각되면 UI가 경고하고, 평균 0.8 미만이면 CloudWatch 알람이 울립니다.
  4. Layer 4 - 클래스 레벨 필드 금지. Reader.political_leaning 같은 정치 성향 추론 필드는 생성과 저장이 금지되며, extra="forbid"가 이를 스키마에서 강제합니다.
  5. Layer 5 - 라이브 시연은 사전 검증된 질문 풀(scripts/eval_wow_queries.py)만 사용합니다.
  6. Layer 6 - 위 4.1의 광고 매칭 거버넌스입니다.

원칙: 거버넌스를 프롬프트 지시에만 맡기지 않고, 스키마(extra="forbid"), 메트릭(balance score), 인프라(Guardrails, 알람)의 세 층에 나눠 강제하는 것이 이 설계의 요지입니다.

0523개 시나리오 개관

시나리오 목록의 단일 진실원은 web/components/Sidebar.tsx:SCENARIOS 배열이며 정확히 23개(A-W)가 등록되어 있습니다. 설계 스펙은 base 14개(A-N)였고, O-S는 사용자 요청 확장, T-W는 실 그래프 엣지 위의 고급 인사이트로 구현 과정에서 늘었습니다. 23개를 개별 서술하는 대신 구현 패턴으로 묶으면 아래 8가지로 압축됩니다.

표 4. 23개 시나리오의 구현 패턴 (CLAUDE.md 시나리오 표, api/routers/ 기준)

23개 시나리오가 21개 라우터와 1:1이 아니라는 점도 코드 이해에 중요합니다. P, Q, R, S 4개는 전용 라우터 없이 의원 디렉토리 데이터와 범용 insight_generic.py로 백킹됩니다. 시나리오 페이지 외에 31클래스 Object Explorer, 온톨로지 관계 그래프(mindmap), 의원 디렉토리(286명, 9개 지표), 운영 콘솔(5 패널), 코드 지식 그래프(codegraph) 페이지가 함께 배포됩니다.

06실제 운영 흐름

배포는 ap-northeast-2 리전에서 npx cdk deploy --all로 6개 스택을 올리는 것으로 시작합니다. VPC는 새로 만들지 않고 자매 프로젝트들과 공유하는 VPC를 import하며(ADR-0006), Neptune은 private subnet에 있어 직접 접근이 불가능합니다. 그래서 데이터 적재는 API 컨테이너 이미지를 재사용하는 one-shot ECS 태스크로 실행합니다.

데이터 적재 - one-shot ECS 태스크 (CLAUDE.md Key Commands)
aws ecs run-task --cluster assembly-dev-cluster --task-definition assembly-dev-api \
  --overrides '{"containerOverrides":[{"name":"api","command":
    ["python","-m","data.load","--source","all","--to","s3",
     "--bucket","assembly-dev-synthetic-data","--neptune","--opensearch"]}]}'

품질 게이트는 두 겹입니다. CI는 push/PR마다 4개 job(python-ast, tsc-check, cdk-synth, pytest)을 돌리고, 배포된 CloudFront를 대상으로 make wow-eval이 84개 케이스(핵심 14개 시나리오 A-N × 6 페르소나)를 평가합니다. README 배지 기준 현재 상태는 84/84 통과, 평균 balance score 0.98이며, 통과율이 85% 미만이거나 중립성 메트릭이 임계값에 미달하면 스크립트가 실패 코드로 종료됩니다. 운영 콘솔(/ops)은 ingest, guardrail, memory, eval, trace 5개 패널로 같은 메트릭을 시연 중에 보여줍니다.

주의 - wow-eval의 범위는 23개 시나리오 전체가 아닙니다

84개 평가 케이스는 base 14개 시나리오(A-N)에 대한 것이며, 확장 시나리오 O-W 9개는 이 자동 평가의 대상이 아닙니다. README도 이를 명시합니다. "wow-eval 100%"를 23개 시나리오 전체의 검증으로 읽으면 과대 해석입니다.

07한계와 결론

7.1 한계

  • PoC 데모입니다. 인증은 edge 계층(Lambda@Edge, API Gateway)에만 있고 API 계층은 upstream을 신뢰하며, DEMO_PUBLIC_MODE 같은 데모 전용 우회가 존재합니다.
  • 독자, 광고, 기사 데이터는 전부 합성입니다. 광고 매칭 거버넌스의 사업적 유효성은 실 인벤토리 없이 검증되지 않았습니다.
  • Bedrock 미연결 시 결정적 mock으로 폴백하고 Stage 2 Tool Use도 시뮬레이션이므로, 화면에 보이는 모든 것이 실 LLM 호출은 아닙니다. 실 데이터 경로(T-W의 Neptune openCypher)와 mock 경로가 혼재합니다.
  • 문서와 코드의 정합은 계속 따라잡는 중입니다. CHANGELOG에 시나리오 수(14 → 23), 클래스 수(25+ → 31), 라우터 수(17 → 21) 정정 기록이 남아 있으며, 이 문서의 수치는 모두 코드 기준입니다.
  • 중립성 가드레일은 한국어 정규식과 사전 검증 질문 풀에 크게 의존합니다. 자유 입력이 늘어나는 production 시나리오에서는 별도 검증이 필요합니다.

7.2 결론

ontology-for-assembly의 가치는 개별 시나리오의 화려함이 아니라 반복 가능한 골격에 있습니다. 실 공공 데이터와 합성 데이터를 스키마 레벨 출처 태깅으로 섞고, 같은 질문에 대한 세 가지 AI 패러다임의 차이를 비교 가능하게 만들고, 민감 도메인의 거버넌스를 프롬프트가 아닌 스키마와 메트릭과 인프라에 나눠 강제하는 구조는 국회 데이터가 아닌 다른 도메인에도 그대로 이식됩니다. 실제로 이 저장소 자체가 화학 도메인 PoC(ontology-for-gcc)의 골격을 차용해 도메인만 교체한 결과물이라는 점이 그 이식성의 증거입니다.

권고: 이 저장소를 참조할 때는 시나리오 코드가 아니라 세 개의 단일 진실원, 즉 data/schemas.py(스키마), PERSONA_REGISTRY(페르소나), Sidebar.tsx:SCENARIOS(시나리오 목록)부터 읽기를 권합니다.
