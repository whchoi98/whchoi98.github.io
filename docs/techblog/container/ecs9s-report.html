ecs9s - AWS ECS 운영을 위한 키보드 중심 터미널 UI 구조 분석

소스 저장소를 기준으로 ecs9s의 Go 패키지 구조, 뷰/내비게이션 모델, ECS Exec 사전 검증과 운영 액션(배포, 스케일, 롤백, 포트포워딩)의 구현 및 실제 배선 상태를 코드 수준에서 분석합니다.

작성 기준일은 2026-08-09입니다.

분석 대상은 ecs9s 소스 저장소(github.com/whchoi98/ecs9s)이며, 버전은 README 배지 기준 v0.1.0으로 git 태그/릴리스는 미발행, 바이너리 버전 문자열은 dev입니다.

빌드 요구 버전은 go.mod 기준 Go 1.24.2입니다.

문서의 모든 수치는 소스 코드(internal/ui/messages.go 등)에서 직접 확인한 값입니다.

요약

  • ecs9s는 Go와 Bubbletea로 만든 ECS 전용 TUI입니다. 21개 리소스 뷰와 실제 배선된 5개 페이지 액션 키(f, e, x, Task/TaskDef의 Ctrl+d)를 터미널 한 화면에 통합하며, 이 수치는 소스 코드의 PageType 열거형과 키 핸들러에서 직접 확인한 값입니다. 도움말에 표기된 S(스케일), b(롤백), Ctrl+f(포트포워딩)는 키 핸들러가 배선되지 않아 아직 동작하지 않습니다.
  • 모든 화면은 Elm 아키텍처(Model-Update-View)를 따르고, AWS API 호출은 tea.Cmd 클로저로 비동기 처리되며, 드릴다운 위치는 NavContext 구조체 하나에 누적됩니다.
  • k9s, e1s에서 영감을 받았지만 차별점은 ECS 특화 운영 액션(강제 재배포, ECS Exec 활성화, 태스크 중지, 태스크 정의 등록 해제 - 스케일/롤백/포트포워딩은 action/ 모듈만 준비된 미배선 상태)과 ECR, ELB, IAM, Cost 같은 주변 서비스 통합 뷰입니다.
  • 콘솔과 CLI를 오가던 조회-진단-조치 루프를 터미널 안에서 끝낼 수 있습니다. 단, ECS Exec 셸은 로컬에 AWS CLI와 session-manager-plugin이 설치되어 있어야 동작합니다.

01문제 정의 - 흩어지는 ECS 운영

ECS 운영의 일상은 화면 왕복입니다. 서비스 배포 상태는 ECS 콘솔에서, 컨테이너 로그는 CloudWatch Logs에서, 이미지 태그는 ECR에서, 알람은 CloudWatch 알람 페이지에서 봅니다. 배포가 이상하면 aws ecs describe-services를 치고, 컨테이너에 들어가려면 aws ecs execute-command의 긴 인자를 다시 조립합니다. 하나의 장애를 진단하는 동안 브라우저 탭과 터미널 사이를 여러 번 오가게 됩니다.

Kubernetes 진영은 이 문제를 k9s로 풀었습니다. 리소스 목록, 드릴다운, 로그, 셸 접속을 키보드만으로 처리하는 터미널 UI가 EKS 운영자의 기본 도구가 되었습니다. ecs9s는 이 경험을 ECS로 가져오는 프로젝트입니다. README는 k9s(Kubernetes), e1s(ECS), tui-aws(AWS)에서 영감을 받았다고 밝히고 있습니다.

기존 도구와의 차별점은 두 가지입니다. 첫째, 조회에 그치지 않는 ECS 특화 운영 액션입니다. 강제 재배포, ECS Exec 활성화, 태스크 중지, 태스크 정의 등록 해제가 각 페이지의 단축키에 연결되어 있습니다. desired count 조정, 이전 태스크 정의로의 롤백, SSM 포트포워딩은 internal/action/에 래퍼 모듈로 준비되어 있으나 아직 단축키에는 배선되지 않았습니다. 둘째, ECS 주변 서비스의 통합 뷰입니다. ECR 이미지, ELB 타겟그룹, IAM 역할, Secrets Manager, 비용 추정까지 21개 뷰가 하나의 탭 구조 안에 들어 있어 진단에 필요한 문맥 전환이 터미널 안에서 끝납니다.

참고 - 이 문서의 수치 검증 방식

README는 21개 뷰, Go 1.24+, 3개 테마를 서술합니다. 이 문서는 해당 수치를 코드에서 재확인했습니다. 뷰 수는 internal/ui/messages.go의 PageType 상수 21개와 internal/ui/pages/의 페이지 파일 21개, Go 버전은 go.mod의 go 1.24.2 선언과 일치했습니다. README와 코드가 어긋나는 수치는 발견되지 않았습니다.

02동작 원리 - TUI 아키텍처

ecs9s는 Go 단일 바이너리입니다. TUI 프레임워크는 Bubbletea(Elm 아키텍처)이고, 스타일은 Lipgloss, AWS 연동은 AWS SDK for Go v2를 씁니다. main.go는 --profile, --region, --theme, --version 네 개의 플래그를 파싱하고, ~/.ecs9s/config.yaml을 읽은 뒤 AWS 세션을 만들어 tea.NewProgram을 시작합니다. CLI 플래그가 설정 파일 값보다 우선합니다.

2.1 계층 구조

코드는 internal/ 아래에서 표현 계층, 데이터 계층, 액션 계층으로 나뉩니다. 표현 계층의 루트는 internal/app/app.go의 App 모델로, 21개 페이지와 8개 재사용 컴포넌트(table, tabs, commandbar, statusbar, help, confirm, logviewer, sparkline)를 합성하고 메시지를 라우팅합니다.

계층패키지내용

2.2 뷰와 내비게이션 모델

모든 뷰의 정체성은 internal/ui/messages.go의 PageType 열거형 하나로 정의됩니다. 각 PageType은 탭 이름(String())과 명령 모드 문자열(Command())을 함께 가지므로, 뷰를 하나 추가하면 탭과 :명령이 같은 자리에서 늘어납니다. 드릴다운 위치는 NavContext 구조체에 담겨 페이지 사이를 이동합니다.

internal/ui/messages.go - 뷰 정의와 드릴다운 컨텍스트 (발췌)
const (
    PageCluster PageType = iota
    PageService
    PageTask
    PageContainer
    PageTaskDef
    // ... Logs, ECR, ELB, ASG, VPC, IAM, Metrics, EC2,
    // ... Events, Stopped, ResMap, Cost, SSM, Secrets, Deploy,
    PageAlarms          // 총 21개
)

// NavContext holds the drill-down context as the user navigates deeper.
type NavContext struct {
    ClusterARN  string
    ClusterName string
    ServiceName string
    ServiceARN  string
    TaskARN     string
    TaskID      string
}

내비게이션은 하이브리드입니다. Tab, [, ]로 탭을 순회하는 경로와, k9s처럼 :service, :ecr, :cost를 입력해 바로 이동하는 명령 모드가 공존합니다. 탭을 전환해도 드릴다운 컨텍스트는 유지되므로, Service에서 특정 서비스로 들어간 뒤 Events나 Metrics 탭으로 옮기면 같은 서비스 범위의 데이터가 나옵니다.

2.3 비동기 AWS API 연동

AWS 호출은 UI 스레드를 막지 않습니다. 각 페이지의 Update()는 API 호출을 tea.Cmd 클로저로 반환하고, Bubbletea 런타임이 이를 고루틴에서 실행한 뒤 결과를 clusterLoadedMsg 같은 타입 메시지로 돌려줍니다. 에러는 ui.ErrorMsg로 승격되어 상태 바에 표시됩니다. 데이터 흐름은 한 방향입니다: 사용자 입력 → App.Update() → Page.Update() → tea.Cmd(AWS API) → 로드 완료 메시지 → Page.View().

참고 - 필터/정렬과 행 선택의 함정

저장소 컨벤션은 테이블에서 선택 행을 읽을 때 Cursor() 인덱스가 아니라 SelectedRow()의 행 데이터를 쓰도록 강제합니다. 커서 인덱스를 원본 배열 인덱스로 쓰면 / 필터나 정렬이 적용된 순간 다른 리소스에 액션이 날아가기 때문입니다. 파괴적 액션이 있는 도구에서는 중요한 설계 결정입니다.

03핵심 메커니즘 딥다이브

3.1 드릴다운과 브레드크럼

탐색의 기본 축은 Cluster → Service → Task → Container 계층입니다. Enter를 누르면 선택 행의 ARN과 이름이 NavContext에 누적되면서 한 단계 내려가고, Esc나 Backspace는 navStack에 쌓인 이전 상태를 복원해 되돌아갑니다. 드릴다운만이 NavContext를 바꾸는 유일한 경로이므로, "지금 어느 클러스터의 어느 서비스를 보고 있는가"가 항상 상태 바에 일관되게 남습니다.

페이지는 두 부류로 나뉩니다. ECR, ELB, VPC, IAM 같은 글로벌 페이지는 컨텍스트 없이 리전 전체를 보여주고 상태 바의 클러스터 표시를 숨깁니다. Service, Task, Events, Metrics 같은 컨텍스트 페이지는 드릴다운 범위로 데이터를 좁힙니다. 명령 모드로 어느 페이지에 점프해도 이 구분이 유지됩니다.

3.2 ECS Exec 셸의 3단계 사전 검증

ECS Exec는 실패 지점이 많은 기능입니다. 로컬 플러그인 누락, 서비스의 enableExecuteCommand 미설정, 에이전트 미기동 중 하나만 걸려도 셸이 열리지 않고, AWS CLI의 에러 메시지만으로는 원인을 찾기 어렵습니다. ecs9s는 Container 뷰에서 x를 누르는 순간 셸 실행 전에 검증을 단계별로 통과시킵니다.

  1. 로컬 도구 검증 - exec.LookPath로 AWS CLI와 session-manager-plugin이 PATH에 있는지 확인하고, 없으면 설치 문서 URL을 포함한 에러를 상태 바에 띄웁니다.
  2. 태스크 상태 검증 - DescribeTasks로 태스크의 enableExecuteCommand 플래그와 ExecuteCommandAgent 관리 에이전트가 RUNNING인지 확인합니다. 실패 사유는 원인별로 다른 문장으로 안내됩니다.
  3. TUI 중단과 복원 - 검증을 통과하면 tea.ExecProcess가 터미널 제어권을 aws ecs execute-command --interactive 서브프로세스에 넘기고, 셸 종료 시 TUI 상태를 그대로 복원합니다.
internal/aws/ecs.go - CheckExecEnabled 검증 (발췌)
for _, ctr := range task.Containers {
    for _, ma := range ctr.ManagedAgents {
        if ma.Name == ecstypes.ManagedAgentNameExecuteCommandAgent {
            result.InitStatus = aws.ToString(ma.LastStatus)
            result.AgentRunning = result.InitStatus == "RUNNING"
        }
    }
}

if !result.TaskExecEnable {
    result.Details = "enableExecuteCommand is not set on this task. ..."
} else if !result.AgentRunning {
    result.Details = "ExecuteCommand agent status: ... may need to be restarted ..."
}
주의 - Exec 활성화 직후에는 셸이 열리지 않습니다

Service 뷰에서 e로 ECS Exec를 활성화하면 서비스에 enableExecuteCommand가 설정되고 강제 재배포가 함께 트리거됩니다. 기존 태스크에는 에이전트가 없으므로, ExecuteCommandAgent를 실은 새 태스크가 뜬 뒤에야 접속이 가능합니다. 또한 Task Role에 ssmmessages:CreateControlChannel 등 4개 채널 권한이 있어야 합니다. 이 대기와 권한이 ECS Exec에서 가장 흔한 혼선 지점입니다.

3.3 운영 액션 - 배포, 스케일, 롤백, 포트포워딩

변경 작업 래퍼는 internal/action/에 6개 모듈(exec, portforward, scale, deploy, rollback, taskdef)로 준비되어 있으나, 현재 배선된 액션은 internal/aws의 클라이언트 메서드를 페이지가 직접 호출합니다. action 모듈 중 실제로 호출되는 것은 ECS Exec 경로의 exec.go뿐입니다. 또한 confirm 컴포넌트는 구현되어 있으나 현재 어떤 액션에도 연결되어 있지 않아, 강제 재배포/태스크 중지/태스크 정의 등록 해제는 확인 다이얼로그 없이 즉시 실행됩니다. 사전 검증이 있는 것은 ECS Exec(x) 경로뿐입니다.

표 2. 페이지별 운영 액션 키 바인딩 (페이지 소스에 키 핸들러가 배선된 5개 기준)
페이지키동작실제 호출 경로

비고 - 도움말에는 표기되어 있으나 키 핸들러가 미배선인 키

Service 뷰의 S(desired count 조정)와 b(이전 태스크 정의로 롤백), Container 뷰의 Ctrl+f(포트포워딩)는 도움말 오버레이에는 표기되어 있으나 키 핸들러가 배선되지 않았습니다. 대응하는 action/scale.go, action/rollback.go, action/portforward.go 모듈은 존재하지만 어디에서도 호출되지 않아, 현재 버전에서 이 세 키는 동작하지 않습니다.

미배선 상태이긴 하지만 롤백 래퍼는 추측하지 않도록 설계되어 있습니다. action/rollback.go의 RollbackService는 먼저 DescribeServices로 PRIMARY 배포의 태스크 정의를 특정하고, 배포 목록에서 그와 다른 태스크 정의를 가진 최근 배포를 롤백 대상으로 고릅니다. 그런 배포가 없을 때만 리비전 번호를 하나 내린 후보를 만들되, DescribeTaskDefinition으로 그 리비전이 실제로 존재하는지 확인한 뒤에야 UpdateService를 호출합니다. 검증에 실패하면 변경 없이 에러로 끝납니다.

포트포워딩 래퍼는 SSM의 AWS-StartPortForwardingSession 문서를 사용합니다. 타겟 식별자는 ecs:{cluster-name}_{task-id}_{runtime-id} 형식인데, 여기에는 ARN이 아니라 짧은 이름이 들어가야 하므로 코드가 ARN에서 이름과 ID를 추출하는 헬퍼를 따로 둡니다. 이 형식을 손으로 조립하다 틀리는 것이 CLI 사용 시 흔한 실수여서 래퍼의 가치는 분명하지만, 이 래퍼를 호출하는 키 핸들러와 포트 입력 UI가 아직 배선되지 않아 현재 버전에서는 사용할 수 없습니다.

현재 상태: confirm 컴포넌트는 구현되어 있으나 어떤 액션에도 연결되어 있지 않아, 강제 재배포/태스크 중지/태스크 정의 등록 해제는 확인 없이 즉시 실행됩니다. 사전 검증을 거치는 것은 ECS Exec(x) 경로뿐입니다.

06한계

코드에서 확인되는 한계를 정리합니다. 프로젝트는 README 배지 기준 v0.1.0(git 태그/릴리스 미발행, 바이너리 버전 문자열은 dev)이고 CHANGELOG가 아직 [Unreleased] 상태이므로, 아래 항목은 현재 시점의 스냅샷입니다.

  • 미배선 액션 - 도움말에 표기된 S(스케일), b(롤백), Ctrl+f(포트포워딩)는 키 핸들러가 배선되지 않아 동작하지 않습니다. action/의 scale, rollback, portforward 모듈은 존재하지만 호출되지 않습니다. confirm 컴포넌트 역시 어떤 액션에도 연결되어 있지 않아, 강제 재배포/태스크 중지/태스크 정의 등록 해제가 확인 다이얼로그 없이 즉시 실행됩니다.
  • 외부 의존 - ECS Exec 셸은 SDK로 직접 구현되지 않고 aws CLI 서브프로세스를 실행합니다(미배선 상태인 포트포워딩 래퍼도 같은 방식입니다). 로컬에 AWS CLI와 session-manager-plugin이 없으면 동작하지 않습니다(사전 검증이 이를 에러로 알려줍니다).
  • 세션 고정 - 프로파일과 리전은 main.go에서 세션을 만들 때 한 번 결정됩니다. 명령 모드의 21개 커맨드는 모두 뷰 전환용이며, 실행 중 프로파일/리전을 바꾸는 커맨드는 없습니다. 멀티 리전 운영이라면 프로세스를 리전별로 띄워야 합니다.
  • 비용 추정의 범위 - Cost 뷰의 단가는 us-east-1 온디맨드 Fargate 값 (vCPU $0.04048/시간, 메모리 $0.004445/GB-시간)으로 코드에 고정되어 있습니다. 다른 리전이나 Savings Plans가 적용된 환경에서는 추정치가 실제 청구액과 다릅니다.
  • 롤백 후보의 한계 - 미배선 상태인 롤백 래퍼(action/rollback.go) 기준으로, 다른 태스크 정의를 가진 배포가 없으면 리비전 번호를 하나 내린 후보를 시도하는데, 그 리비전이 이미 등록 해제되었다면 존재 검증에 걸려 롤백이 에러로 끝납니다. 안전하지만, 이 경우 수동으로 대상 리비전을 골라야 합니다.
  • 설치 경로 - 별도의 릴리스 바이너리 배포 없이 소스 빌드가 유일한 설치 방법이므로 Go 툴체인이 필요합니다.

07결론

ecs9s는 k9s가 Kubernetes 운영자에게 준 "터미널 안에서 끝나는 루프"를 ECS에 맞게 다시 만든 도구입니다. 같은 계열의 e1s와 비교했을 때 이 프로젝트가 힘을 준 곳은 ECS의 실제 운영 동선입니다. 강제 재배포, ECS Exec 활성화, 태스크 중지, 태스크 정의 등록 해제가 단축키로 연결되어 있고 (스케일, 롤백, 포트포워딩은 래퍼 모듈만 준비된 미배선 상태입니다), ECR부터 비용 추정까지 주변 서비스 21개 뷰가 하나의 내비게이션 모델 안에 들어 있습니다.

구현 관점에서 눈여겨볼 부분은 실패를 앞당기는 설계입니다. ECS Exec의 3단계 사전 검증, 미배선 롤백 래퍼의 대상 존재 확인, SelectedRow 기반 행 선택, SecureString 비복호화 같은 결정이 "조회는 편하게, 변경은 보수적으로"라는 방향을 지향합니다. 다만 confirm 다이얼로그가 아직 어떤 액션에도 연결되어 있지 않아, 변경 액션의 안전장치는 현재 ECS Exec 사전 검증에 한정됩니다. ECS를 콘솔과 CLI로 오가며 운영하고 있다면, 단일 바이너리 하나로 시도해 볼 비용이 충분히 낮은 도구입니다.

ecs9s - Inside a Keyboard-Driven Terminal UI for AWS ECS Operations

Based on the source repository, this document analyzes ecs9s at the code level: its Go package structure, view/navigation model, ECS Exec preflight validation, and the implementation and actual wiring status of its operational actions (deploy, scale, rollback, port forwarding).

Written as of 2026-08-09.

The subject is the ecs9s source repository (github.com/whchoi98/ecs9s); the version is v0.1.0 per the README badge, with no git tags/releases published and a binary version string of dev.

The required build version is Go 1.24.2 per go.mod.

Every number in this document was verified directly in the source code (internal/ui/messages.go and others).

TL;DR

  • ecs9s is an ECS-dedicated TUI built with Go and Bubbletea. It brings 21 resource views and 5 actually wired page action keys (f, e, x, and Ctrl+d on Task/TaskDef) into a single terminal screen; these numbers were verified directly in the source, in the PageType enum and key handlers. The S (scale), b (rollback), and Ctrl+f (port forwarding) keys shown in the help overlay have no wired key handlers and do not work yet.
  • Every screen follows the Elm architecture (Model-Update-View), AWS API calls run asynchronously as tea.Cmd closures, and the drill-down position accumulates in a single NavContext struct.
  • Inspired by k9s and e1s, its differentiators are ECS-specific operational actions (force redeploy, ECS Exec enablement, task stop, task definition deregistration - scale/rollback/port forwarding exist only as unwired action/ modules) and integrated views of surrounding services such as ECR, ELB, IAM, and Cost.
  • The inspect-diagnose-act loop that used to bounce between the console and the CLI can now finish inside the terminal. Note that the ECS Exec shell requires the AWS CLI and session-manager-plugin to be installed locally.

01Problem - ECS Operations Scattered Everywhere

Day-to-day ECS operations means bouncing between screens. Service deployment status lives in the ECS console, container logs in CloudWatch Logs, image tags in ECR, and alarms on the CloudWatch alarms page. When a deployment misbehaves you type aws ecs describe-services, and to get into a container you reassemble the long arguments of aws ecs execute-command yet again. Diagnosing a single incident means switching between browser tabs and the terminal many times.

The Kubernetes world solved this with k9s: a terminal UI that handles resource lists, drill-down, logs, and shell access with the keyboard alone became the default tool for EKS operators. ecs9s is a project that brings that experience to ECS. The README states it was inspired by k9s (Kubernetes), e1s (ECS), and tui-aws (AWS).

It differs from existing tools in two ways. First, ECS-specific operational actions that go beyond read-only browsing. Force redeploy, ECS Exec enablement, task stop, and task definition deregistration are bound to shortcut keys on their pages. Adjusting the desired count, rolling back to a previous task definition, and SSM port forwarding exist as wrapper modules in internal/action/ but are not yet wired to shortcut keys. Second, integrated views of the services around ECS. ECR images, ELB target groups, IAM roles, Secrets Manager, and even cost estimation - 21 views live inside one tab structure, so the context switching a diagnosis requires ends inside the terminal.

Note - How the numbers in this document were verified

The README describes 21 views, Go 1.24+, and 3 themes. This document re-verified those numbers in the code. The view count matched the 21 PageType constants in internal/ui/messages.go and the 21 page files in internal/ui/pages/; the Go version matched the go 1.24.2 declaration in go.mod. No numbers were found where the README and the code disagree.

02How It Works - TUI Architecture

ecs9s is a single Go binary. The TUI framework is Bubbletea (Elm architecture), styling uses Lipgloss, and AWS integration uses the AWS SDK for Go v2. main.go parses four flags - --profile, --region, --theme, --version - reads ~/.ecs9s/config.yaml, creates the AWS session, and starts tea.NewProgram. CLI flags take precedence over config file values.

2.1 Layered Structure

Under internal/ the code splits into a presentation layer, a data layer, and an action layer. The root of the presentation layer is the App model in internal/app/app.go, which composes 21 pages and 8 reusable components (table, tabs, commandbar, statusbar, help, confirm, logviewer, sparkline) and routes messages between them.

Table 1. Composition by layer (based on internal/ packages)
LayerPackagesContents
Presentation app, ui/pages, ui/components, ui/styles, theme Root model and routing, 21 page models, 8 widgets, Lipgloss styles, 3 theme presets (dark, light, blue)
Data aws 10 SDK v2 client wrapper files - ecs, cloudwatch, ecr, elb, ec2, iam, autoscaling, ssm, secrets, session
Action action 6 mutation wrapper modules - exec, portforward, scale, deploy, rollback, taskdef (only exec is currently called)
Config config ~/.ecs9s/config.yaml loader (profile, region, theme)

2.2 View and Navigation Model

The identity of every view is defined by a single PageType enum in internal/ui/messages.go. Each PageType carries both a tab name (String()) and a command-mode string (Command()), so adding one view grows the tab bar and the : commands in the same place. The drill-down position travels between pages inside the NavContext struct.

internal/ui/messages.go - view definitions and drill-down context (excerpt)
const (
    PageCluster PageType = iota
    PageService
    PageTask
    PageContainer
    PageTaskDef
    // ... Logs, ECR, ELB, ASG, VPC, IAM, Metrics, EC2,
    // ... Events, Stopped, ResMap, Cost, SSM, Secrets, Deploy,

    ClusterARN  string
    ClusterName string

}

Navigation is hybrid. A path that cycles tabs with Tab, [, and ] coexists with a k9s-style command mode where typing :service, :ecr, or :cost jumps straight to a view. Switching tabs preserves the drill-down context, so after drilling into a specific service from the Service view, moving to the Events or Metrics tab shows data scoped to that same service.

2.3 Asynchronous AWS API Integration

AWS calls never block the UI thread. Each page's Update() returns the API call as a tea.Cmd closure; the Bubbletea runtime executes it on a goroutine and delivers the result back as a typed message such as clusterLoadedMsg. Errors are promoted to ui.ErrorMsg and shown in the status bar. Data flows in one direction: user input → App.Update() → Page.Update() → tea.Cmd (AWS API) → loaded message → Page.View().

Note - the filter/sort vs. row-selection trap

The repository convention mandates reading the selected table row via SelectedRow() row data, not the Cursor() index. If the cursor index were used as an index into the original array, an action would hit a different resource the moment a / filter or a sort is applied. For a tool with destructive actions, this is an important design decision.

03Core Mechanism Deep Dive

3.1 Drill-down and Breadcrumbs

The primary axis of navigation is the Cluster → Service → Task → Container hierarchy. Pressing Enter descends one level while accumulating the selected row's ARN and name into NavContext; Esc or Backspace restores the previous state pushed onto navStack. Because drilling down is the only path that mutates NavContext, "which service of which cluster am I looking at right now" stays consistently visible in the status bar.

Pages fall into two groups. Global pages such as ECR, ELB, VPC, and IAM show the whole region without any context and hide the cluster indicator in the status bar. Context pages such as Service, Task, Events, and Metrics narrow their data to the drill-down scope. Jumping to any page via command mode preserves this distinction.

3.2 The 3-Stage Preflight Validation for the ECS Exec Shell

ECS Exec is a feature with many failure points. A missing local plugin, an unset enableExecuteCommand on the service, or an agent that never started - any one of these keeps the shell from opening, and the AWS CLI's error messages alone make the cause hard to find. The moment you press x in the Container view, ecs9s walks through validation stages before launching the shell.

  1. Local tooling check - exec.LookPath verifies that the AWS CLI and session-manager-plugin are on PATH; if not, an error including the installation docs URL is shown in the status bar.
  2. Task state check - DescribeTasks verifies the task's enableExecuteCommand flag and that the ExecuteCommandAgent managed agent is RUNNING. Each failure cause is explained with a different message.
  3. TUI suspend and restore - once validation passes, tea.ExecProcess hands terminal control to the aws ecs execute-command --interactive subprocess, and restores the TUI state intact when the shell exits.
internal/aws/ecs.go - CheckExecEnabled validation (excerpt)
for _, ctr := range task.Containers {
    for _, ma := range ctr.ManagedAgents {
        if ma.Name == ecstypes.ManagedAgentNameExecuteCommandAgent {
            result.InitStatus = aws.ToString(ma.LastStatus)
            result.AgentRunning = result.InitStatus == "RUNNING"
        }
    }
}

if !result.TaskExecEnable {
    result.Details = "enableExecuteCommand is not set on this task. ..."
} else if !result.AgentRunning {
    result.Details = "ExecuteCommand agent status: ... may need to be restarted ..."
}
Warning - the shell does not open right after enabling Exec

Enabling ECS Exec with e in the Service view sets enableExecuteCommand on the service and triggers a force redeploy along with it. Existing tasks have no agent, so you can connect only after new tasks carrying the ExecuteCommandAgent have started. The Task Role also needs the 4 channel permissions such as ssmmessages:CreateControlChannel. This wait and these permissions are the most common source of confusion with ECS Exec.

3.3 Operational Actions - Deploy, Scale, Rollback, Port Forwarding

Mutation wrappers exist as 6 modules in internal/action/ (exec, portforward, scale, deploy, rollback, taskdef), but the currently wired actions call internal/aws client methods directly from the pages. The only action module actually invoked is exec.go on the ECS Exec path. The confirm component is implemented but not connected to any action, so force redeploy / task stop / task definition deregistration execute immediately without a confirmation dialog. The only path with preflight validation is ECS Exec (x).

Table 2. Operational action key bindings per page (the 5 with key handlers wired in the page sources)

Remark - keys shown in the help overlay but with no wired handler

S (adjust desired count) and b (roll back to the previous task definition) in the Service view, and Ctrl+f (port forwarding) in the Container view, appear in the help overlay but have no wired key handlers. The corresponding action/scale.go, action/rollback.go, and action/portforward.go modules exist but are never called, so these three keys do nothing in the current version.

Although unwired, the rollback wrapper is designed not to guess. RollbackService in action/rollback.go first identifies the PRIMARY deployment's task definition via DescribeServices, then picks as the rollback target the most recent deployment in the list with a different task definition. Only when no such deployment exists does it construct a candidate by decrementing the revision number - and even then it calls DescribeTaskDefinition to confirm the revision actually exists before calling UpdateService. If validation fails, it ends in an error with no changes made.

The port forwarding wrapper uses SSM's AWS-StartPortForwardingSession document. The target identifier has the form ecs:{cluster-name}_{task-id}_{runtime-id}, which requires short names rather than ARNs, so the code keeps a dedicated helper that extracts names and IDs from ARNs. Hand-assembling this format is a common mistake when using the CLI, so the wrapper's value is clear - but the key handler and port input UI that would call it are not wired yet, so it cannot be used in the current version.

Current state: the confirm component is implemented but connected to no action, so force redeploy / task stop / task definition deregistration execute immediately without confirmation. The only path that goes through preflight validation is ECS Exec (x).

The Cost view does not guess from names: it computes hourly/daily/monthly cost from the actual vCPU and memory values returned by DescribeTaskDefinition. The SSM view calls with WithDecryption: false so SecureString values never reach memory, and masks them on screen as ****. For a read-oriented tool handling secret values, this is a conservative choice.

05Real Operational Flow

5.1 Install and Run

Distribution is a single binary produced by go build. Clone the repository, build, and move it onto your PATH - that is all.

In the shell - install and launch
git clone https://github.com/whchoi98/ecs9s.git
cd ecs9s
go build -o ecs9s .          # Go 1.24.2 or later
sudo mv ecs9s /usr/local/bin/

ecs9s --profile myprofile --region ap-northeast-2 --theme dark

Store frequently used values in ~/.ecs9s/config.yaml. If the same key is also given as a CLI flag, the flag wins.

~/.ecs9s/config.yaml
aws:
  profile: default
  region: ap-northeast-2
theme: dark    # dark | light | blue

5.2 A Deployment Incident Diagnosis Scenario

Assume "5xx errors rose after a deployment". The flow goes like this: jump to :service and check the running/desired mismatch, press Enter to descend into tasks, and read the stop reasons in :stopped. View container logs with :log, and if you need to dig deeper, descend to Container and open a shell with x. If the cause is the new image you need a rollback - but the b key shown in the help overlay is not wired yet, so in the current version you must revert with aws ecs update-service, specifying the previous task definition. Aside from the rollback, nothing in this loop requires opening a browser.

06Limitations

These are the limitations visible in the code. The project is at v0.1.0 per the README badge (no git tags/releases, binary version string is dev) and the CHANGELOG is still [Unreleased], so the items below are a snapshot of the current state.

  • Unwired actions - S (scale), b (rollback), and Ctrl+f (port forwarding) shown in the help overlay have no wired key handlers and do not work. The scale, rollback, and portforward modules in action/ exist but are never called. The confirm component is likewise connected to no action, so force redeploy / task stop / task definition deregistration execute immediately without a confirmation dialog.
  • External dependencies - the ECS Exec shell is not implemented directly against the SDK; it runs an aws CLI subprocess (the unwired port forwarding wrapper works the same way). It will not work without the AWS CLI and session-manager-plugin installed locally (the preflight validation reports this as an error).
  • Session pinning - profile and region are decided once when main.go creates the session. All 21 command-mode commands are for view switching; there is no command to change profile/region at runtime. For multi-region operations you must run one process per region.
  • Cost estimation scope - the Cost view's unit prices are hard-coded to us-east-1 on-demand Fargate values (vCPU $0.04048/hour, memory $0.004445/GB-hour). In other regions or in environments with Savings Plans applied, estimates will differ from the actual bill.
  • Rollback candidate limits - based on the unwired rollback wrapper (action/rollback.go): when no deployment with a different task definition exists, it tries a candidate with the revision number decremented by one, and if that revision has already been deregistered the existence check fails and the rollback ends in an error. Safe, but in that case you must pick the target revision manually.
  • Installation path - there is no released binary distribution; building from source is the only installation method, so a Go toolchain is required.

07Conclusion

ecs9s rebuilds for ECS the "loop that finishes inside the terminal" that k9s gave Kubernetes operators. Compared with e1s in the same family, where this project puts its weight is the actual ECS operational workflow. Force redeploy, ECS Exec enablement, task stop, and task definition deregistration are bound to shortcuts (scale, rollback, and port forwarding remain unwired with only their wrapper modules prepared), and 21 views spanning surrounding services - from ECR to cost estimation - live inside one navigation model.

From an implementation standpoint, the design that moves failure earlier is worth noting. The 3-stage ECS Exec preflight validation, the unwired rollback wrapper's target existence check, SelectedRow-based row selection, and non-decryption of SecureStrings all point in the same direction: "make reads easy, keep writes conservative". That said, the confirm dialog is not yet connected to any action, so the safety net for mutating actions is currently limited to the ECS Exec preflight validation. If you operate ECS by bouncing between the console and the CLI, this is a tool whose single binary makes it cheap enough to simply try.
